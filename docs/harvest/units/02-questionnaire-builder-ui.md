### aggregateResponses — the shape to port

Discriminated on `chart`, seven members in the donor: `choice :63`, `scale :68`, `rating :77`, `boolean :83`, `text :89`, `timeline :95`, `grid :103`. Every member extends `AggregateBase {questionId, prompt, questionKind, responded, skipped, total}` (built at `:174-181`). The rules worth copying digit-exact: the Google-Forms denominator is *respondents who answered THAT question*, not total respondents; `pct = Math.round((count / denominator) * 1000) / 10`; `average = Math.round((sum / n) * 100) / 100`, `null` at `n === 0`; a **deleted option still gets a row**, labelled by its raw value (`:209-217`); an out-of-range scale value gets an appended bucket rather than being dropped (`:371-376`); answers whose question no longer exists become `orphans: {questionId, count}[]` (`:119`, `:396-408`) rather than vanishing. Kind-map for Camp 404: drop `grid` and `rating` (no such kinds), **drop or captain-gate `text`** — `docs/questionnaire-builder.md:400` rules free-text out of value breakdown as PII — and *add* a numeric-summary shape (min/max/avg/median) the donor lacks but Camp 404's §7.2 wants for `slider` continuous. `displayResponseValue` (`packages/types/src/questionnaire.ts:321-350`) already does the id→label resolution the donor hand-rolls, so the port is smaller than 419 lines suggests.

### CSV — the four mechanics that are each a paid-for bug

From `results-view.tsx:505-609`: `csvCell` wraps every value in double quotes and **doubles inner quotes** (`:551`); lines join with `\r\n`; the file is prefixed with a **UTF-8 BOM** so Excel doesn't mojibake member names (`:587-589`); download is `Blob` + `URL.createObjectURL` + a synthetic `<a download>` click + `revokeObjectURL` (`:590-597`). Header is `["Recipient","Status","Completed", ...questions.map(q => q.prompt)]`. Skip the donor's `optionLabelMap` keyed `${q.id}:${o.value}` — build the cell formatter over `displayResponseValue` instead so Camp 404 keeps one label-resolution path. WP9 #133 also wants a roster CSV, so put `csvCell` + the BOM in a shared helper.

### DefinitionIssue — and the two checks Camp 404 is actually missing

`validateBuilderQuestionnaire` checks title, empty pages, earlier-only `visibleIf`, image alt text, inputs-on-content-pages, `options.length >= 2`, `inputCount > 0`, and satisfiability. It has **no duplicate-id check** and **no duplicate-option-value check** — verified by reading the whole function. `OptionsEditor` dedupes on insert (`options-editor.tsx:27-37`) but a stored definition with duplicate values publishes clean, and duplicate question ids silently collide in the flat responses map (reachable via `duplicateDraftAction` or hand-edited JSONB). Adopt the donor's `DefinitionIssue {path, code, message}` shape with this mapped vocabulary: `duplicate_id`, `duplicate_option_value`, `invalid_range`, `dangling_visible_if`, `no_visible_page`. **Do not** take `unreachable_page`, `unknown_branch_target`, `backward_branch`, `self_branch`, `reserved_id`, `reserved_option_value` — Camp 404 has no jump targets and no `SUBMIT_TARGET`/`OTHER_PREFIX` constants. Path grammar differs: `pages[i].blocks[j]` with the question one level deeper (`.question.options[k]`), not the donor's `pages[i].questions[j]`. And **do not** take the donor's "a definition that fails validation is never written" rule — `updateDefinitionAction` (`actions.ts:128-147`) is the canvas autosave and must keep persisting half-built drafts. Only the return SHAPE ports.

### The three small defects this comparison exposed (fix these first, they're nearly free)

1. `builder-wizard.tsx:237` is `return <ContentBlockRenderer key={block.id} block={block} />;` with no `visibleIf` check — verified. Meanwhile all four content blocks carry `...visibility` (`questionnaire-builder.ts:52-98`, verified), `validateBuilderQuestionnaire` validates their `visibleIf` references, and `classifyChange` treats edits to them as breaking. So a captain can author a conditional explainer and the runner shows it always. One `if`.
2. `apps/web/app/questionnaires/[activationId]/runner.tsx` is 32 lines taking four props and hardcodes `variant="runner"` — verified by reading the whole file. `activation.blocking` is selected into `ActivationRow` (`activations.ts:236`) and never threaded through, so a non-blocking send renders `BlockingTopBar` + `BlockingNotice` + "Required".
3. `getPendingRequiredActions` filters `eq(requiredActions.blocking, true)` **in SQL** (`activations.ts:229`, verified) *before* `nextGate`'s own `if (!action.blocking) continue;` (`required-actions.ts:32`). A non-blocking row is never even read. Combined with there being no listing surface, WP4 #128 is exact: the default send reaches nobody.
