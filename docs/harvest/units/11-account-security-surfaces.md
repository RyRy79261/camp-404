# 11 — account-security-surfaces

**Headline:** Ship the sessions + security-event + sole-captain-deletion-guard triad; the sole-captain guard starts with a one-line fix to a **live bug** (`packages/db/src/bootstrap.ts` counts captains without filtering `sanitised`/`isSystem`), and every 2FA/passkey asset is provider-blocked, not merely unbuilt.

**Camp 404 today:** Zero account-security surfaces — no session list, no security feed, no bespoke password screen (`apps/web/app/auth/[path]/page.tsx` delegates forgot/reset to Neon's hosted `<AuthView>`), no `loading.tsx` anywhere under `apps/web/app` (only `error.tsx` and `not-found.tsx` at the root). Erasure ships but is immediate and unguarded: `deleteOwnAccount` (`apps/web/app/profile/actions.ts:55-69`) checks auth + camp access + a typed `DELETE` and nothing else, then calls `sanitiseAccount` (`packages/db/src/account.ts:55-130`).

**Gating fact, verified directly in the installed typings** (`node_modules/.pnpm/@neondatabase+auth@0.4.1-beta_.../dist/next/{index,server/index}.d.mts`): `twoFactor`, `totp`, `backupCode`, `passkey` = **0 hits in both**. The runtime plugin array is closed — `supportedBetterAuthClientPlugins` in `dist/adapter-core-BFMM3lwe.mjs:725-732` is exactly `[jwtClient, adminClient, organizationClient, emailOTPClient, magicLinkClient, anonymousTokenClient]`. Present client+server: `listSessions`, `revokeSession`, `revokeSessions`, `revokeOtherSessions`, `changePassword`, `listAccounts`, `deleteUser`, `resetPassword`. **Client-only** (0 server hits): `changeEmail`, `unlinkAccount`, `linkSocial`, `forgetPassword`.

**Tombstone-aware counting — the live bug.** `getBootstrapState()` runs `select count(*)::int from users where rank = 'captain'` (`packages/db/src/bootstrap.ts:23-26`) and `bootstrapFirstCaptain()` repeats it inside its transaction at `:75-78`. Neither filters `sanitised = false` or `isSystem = false`. `sanitisedUserPatch` (`packages/db/src/account.ts:21-43`) deliberately **preserves `rank`** — I read the returned object; there is no rank key. So an erased captain still counts. After a sole captain erases themselves, `isCampBootstrapped()` (`apps/web/lib/bootstrap.ts:25`) returns true on *both* arms (`captainCount > 0 || bootstrappedAt !== null`) and `bootstrapFirstCaptain` returns `already-bootstrapped` — `/setup` is closed by a ghost. The habit already exists elsewhere: `packages/db/src/roster.ts:93` filters `and(isSystem=false, sanitised=false)` and `packages/db/src/audience.ts:35` does the same. Fix is one `and(...)` in two places, testable in-process on the PGlite harness.

**`assessDeletionEligibility`.** Shape: `(ctx) => { ok, blocks: DeletionBlock[], warnings: DeletionWarning[] }`, every block returned at once, each carrying a message the UI renders verbatim. Donor block codes `sole_camp_lead | sole_org_god | no_sign_in_method` collapse to a single `sole_captain` (`rankEnum` is `[captain, member]`, `schema.ts:40`); drop `no_sign_in_method` — it is unverifiable against a managed provider. Drop all three warning codes (`supplier_onboarding_in_flight`, `org_access_revoked`, `supplier_listing_released` — donor `:309-314`), all org/supplier. Keep the `groupIds`-equivalent payload so the block can deep-link a transfer; in Camp 404 that destination is WP3 #127's captain-promotion handshake, which makes the two mutually enabling. Guard belongs in `deleteOwnAccount` between `hasCampAccess` and the `DELETE` check, and again at erasure time if a grace period ever lands (donor's two-managers worked example, `apps/web/lib/account-sanitize.ts:124-136`). One recovery lever the digest surfaced: `API_ENDPOINTS.admin` exposes `setRole`/`createUser` server-side, so a stranded camp is recoverable via a Neon-admin path — not via `/setup`.

**`AccountSessions`.** Pure presentation; both actions injected as props returning `{ok:true,message?}|{ok:false,error}`. Props: `sessions: SessionView[]` where `SessionView = {token, label, ipAddress, lastSeen, current}`, plus `onRevoke(token)`, `onRevokeOthers()`, `onChanged?`. Deps are `badge`/`button`/`toast`, all API-compatible in Camp 404 (`badge.tsx` has `success` + `outline`; `toast.success(title, opts)`). Keep three decisions verbatim: show the **IP, never a geolocated city** ("an invented city is a security lie", donor `:13-21`); label the bulk control "Sign out everywhere **else**"; and the empty state that says the list is **unavailable**, not that nothing is signed in (`:112-117`). `relative()` bands: `<2min` "Active now", `<60min` "N minutes ago", `<24h` "N hour(s) ago", else "N day(s) ago", null/NaN → "Last seen unknown". **Wiring caveat that raises effort to M/L:** Camp 404's server instance is a remote fetch proxy that writes rotated cookies through Next's cookie store, so `auth.listSessions()` inside an RSC render hits the exact failure documented at `apps/web/lib/auth.ts:43-57`. Use a route handler, or the same degraded-read fallback (`readSessionWithoutCookieWrite`).

**`AUTH_CAPABILITIES`.** A record keyed by capability, each entry `{key, support, method, reason, userMessage?, pending?, pendingMessage?}`. `support` has **three** members — `supported | client_only | unavailable` — and `client_only` is exactly Camp 404's live state for `changeEmail`, `unlinkAccount`, `linkSocial`, `forgetPassword` (verified: 0 server hits, present in the client typings). Do not collapse to two. `pending: true` is the separate "supported but not finished" flag — that is Camp 404's state for `sessionList`/`sessionRevoke` today. Also port `capabilityPendingMessage` and `capabilityIsUsable` (donor `:62-68`), which is what lets a call site render a disabled control *with* a reason, plus `assertCapability(key)` as a fail-closed server gate. Copy the two tests in intent: every key covered exactly once, every entry documents WHY. Note the donor's own preamble (`auth-capabilities.ts:1-23`) records that it **ran on managed Neon Auth first** and shipped 2FA/passkeys as honest "not available yet" cards — that history is the reference implementation for Camp 404's exact target state.

**`security_events`.** Donor table: `id uuid PK, user_id → users ON DELETE CASCADE, kind securityEventKindEnum, ip text, user_agent text, created_at` with index `(user_id, created_at DESC)`; it is a **purged** table at sanitisation because ip/user_agent are personal data. Camp 404's realistic kind set is 6, not 9: `password_changed, password_reset_completed, session_revoked, sessions_revoked_others, deletion_requested, deletion_cancelled` (the three email-change kinds drop with the email-change skip). Titles live in `@camp404/core`, never in the DB, so a wording change needs no migration; the app composes the detail line (`${deviceLabel(ua)} · ${ip}`) itself. Add a dedicated table rather than reviving `audit_log` (`schema.ts:1180-1196`, **zero writers and zero readers** — confirmed, the only repo hit is the schema definition): `audit_log` is actor-acting-on-target shaped, a security feed is subject-shaped. Keep the `note` prop naming what the feed omits — Camp 404's feed will omit more than the donor's.

## Deliberately skip

- **All 2FA** (`account-two-factor.tsx` 618, `account-two-factor-challenge.tsx` 137) and **all passkeys** (`account-passkeys.tsx` 275) — no provider. `@better-auth/passkey@1.4.9` in the pnpm store is a transitive of `@daveyplate/better-auth-ui` and is not wired into `createAuthClient()`. Shipping these would be 1,030 lines that always error.
- **Email-change 48h state machine** — Camp 404's `users` table has no email column at all; identity email is Neon's, and `changeEmail` is client-only. The donor ships its own version **disabled** with a comment about permanent account takeover.
- **`AccountDeleteElsewhere`** — pure three-app artefact.
- **Unlink control on a sign-in-methods card** — `unlinkAccount`/`linkSocial` are client-only, so the donor's stated model ("the list is not the boundary, the server predicate is") is unimplementable here. Ship the card read-only or not at all.
- **Bespoke forgot/reset forms** — buildable, but wraps a flow Neon owns and whose email Camp 404 cannot send. Take the two principles instead (confirmation rendered *in place of* the form, not by redirect; a missing token is a different screen, not a disabled state).
- **Email transport / `sendAuthEmail` seam** — Camp 404 has zero email vendors and a working in-app inbox + push. Route security notices through `packages/db/src/broadcasts.ts` instead.
- **`account-tokens.ts`** — its only consumer is the skipped email-change flow; the technique already exists at `apps/web/lib/mcp/tokens.ts` and `cron-auth.ts`.
- **`AccountShell`** — over-structure for two or three tabs in a single app. Take only "sections as props" and "plain `<nav>` of links, not Tabs, because these are separate routes". Use `next/link`, not the donor's plain `<a>` (that was multi-app coupling).
- **The `apps/org` / `apps/suppliers` account fork** — ~1,400 near-duplicate lines; the donor's own audit calls it a fork. Take the `apps/web` variant only.

## DB changes this unit implies

- `security_events` table: `id uuid PK, user_id uuid → users ON DELETE CASCADE, kind security_event_kind, ip text, user_agent text, created_at timestamptz default now()`, index `(user_id, created_at DESC)`. Add to the purge list in `sanitiseAccount`.
- New enum `security_event_kind`: `password_changed, password_reset_completed, session_revoked, sessions_revoked_others, deletion_requested, deletion_cancelled`.
- `action_rate_limit` table: `key text PK, count integer NOT NULL, window_start bigint NOT NULL`, index on `window_start`. Keep it **separate** from any provider-owned limiter table — the donor's 21-line comment records that sharing one silently cut a 15-minute budget to 60 seconds.
- **Decision-gated, not implied:** `account_deletion_requests` (with the partial unique index on `user_id WHERE status='pending'`) only if the owner reverses the recorded "irreversible" decision.
- Migrations are drizzle-kit-generated and append-only (AGENTS.md).

## Corrections applied

- **REFUTED (asset 1, `AccountAuthClient`):** the stated payoff ("`packages/ui` is also consumed by `apps/mobile` and `apps/admin-cli`") is false — only `apps/web` depends on `@camp404/ui`. A DI interface for one consumer is over-structure. Keep `ClientResult<T>` and `clientErrorMessage` verbatim; drop the interface indirection. **INSPIRE, not ADAPT.**
- **REFUTED (asset 9, sign-in methods):** `unlinkAccount`/`linkSocial` are client-only. I re-verified: 0 hits in `dist/next/server/index.d.mts`. Value drops medium → low; read-only card or nothing.
- **REFUTED (asset 13, enumeration guard):** the proposed extension to `/api/tools/invite/check` and `/signup/required` is wrong — those are *invite-code* oracles whose responses (`{available, reason, hint}`) can never match any of the 12 substrings, and both are already auth-gated and rate-limited (shipped as B4 of the auth-surface-hardening spec). The enum genuinely collapses to `sign_in` + `sign_up`.
- **REFUTED (asset 14, 14-day grace period):** irreversibility is a **recorded owner decision** (`docs/superpowers/specs/2026-05-30-account-deletion-design.md` §Decisions, plus §Deferred rejecting hard-delete), not an omission. This is a product question needing sign-off, not an L-sized port. The strongest case for reopening it: `sanitisedUserPatch` severs `authUserId`, so a misclick is genuinely unrecoverable.
- **REFUTED (asset 29, guard counting):** verdict was MISSING; it is **PARTIAL** — the query exists twice and is missing its filter. Re-verified in code (above). This is a shipped defect, which raises its priority to #1 in the unit.
- **REFUTED (asset 40, route-group carve-out):** the "live defect" framing is wrong. Erasure *capability* is not lost — `deleteOwnAccount` re-gates only on auth + camp access, never `isApproved`, so the server action stays network-reachable; only the UI route is gated. The repo already documents this asymmetry the other way round (`design/feature-set/08-profile-edit.md:133`), and an earlier `!profile?.completedAt` redirect blocks a strictly larger population than `isApproved` does. The decision needed is *which side to align*, not a carve-out.
- **REFUTED (asset 42, session lifetime):** the digest downgraded this to INSPIRE on the grounds that Camp 404 cannot set the value. It can — `cookies.sessionDataTtl` is a documented `createNeonAuth` option (confirmed, 5 hits in the server typings) and `apps/web/lib/neon-auth.ts` simply omits it. Promoted to a quick win.
- **My own spot-check, correcting the verifier's MISSED list:** the claim "Camp 404 has zero `not-found.tsx` files anywhere under `apps/web/app`" is **false** — `apps/web/app/not-found.tsx` exists (30 lines). Zero `loading.tsx` and exactly one `error.tsx` are both confirmed. Port `not-found-view.tsx` only for *nested* dynamic routes, not as a missing root.
- **My own spot-check:** the digest describes the closed plugin list as "exactly eight plugin ids". The runtime array (`dist/adapter-core-BFMM3lwe.mjs:725-732`) holds **six** client plugins. The conclusion is unchanged and stronger: no `twoFactor`, no `passkey`, and the list is not runtime-configurable.
