# 12 — privacy, PII, retention, deletion

**Headline:** Camp 404 has a live data-destruction bug on the encrypted-ID write path — one ordinary questionnaire re-save on a key-rotated deployment permanently overwrites a member's ID ciphertext with `null` under a "Saved" toast. The donor's `decryptField` tri-state + `encryptOrPreserve` fix it in under an hour; take those first, then the two cheap invariant tests, then the sole-captain deletion guard.

**Camp 404 today:** It owns the encryption half and almost none of the privacy/retention/deletion-lifecycle half. Shipped: `packages/db/src/crypto.ts` (byte-equivalent to the donor's minus `decryptField`; `KEY_SALT = "camp404-pgcrypto-v1"`), four encrypted columns (`schema.ts:269-271`, `:766`), a boot-time `PGCRYPTO_KEY` gate (`apps/web/lib/env.ts:20-26`), a server-enforced public/captain roster fork (`apps/web/lib/camp-roster.ts`, `public-member.ts:35-42` + invariant tests), a `sanitised`/`lostCatNumber` tombstone with a pure patch + pooled transaction (`packages/db/src/account.ts`), and a live `redactPii`/`sanitizeReportText` (`packages/core/src/text-redaction.ts`). Missing entirely: any `privacy_flags` column, any deletion grace period or eligibility guard (`apps/web/app/profile/actions.ts:55-68` erases immediately behind a typed "DELETE"), any ID-retention rule, any audit_log writer (`schema.ts:1180` has zero), and any coverage threshold in any of the 8 vitest configs.

**`decryptField`** — paste below `decryptOrNull`, keep both. Union: `{state:"empty",value:null} | {state:"ok",value:string} | {state:"unreadable",value:null}`; body is `if (!stored) return EMPTY_FIELD; try { return {state:"ok", value: decrypt(stored)} } catch { return {state:"unreadable", value:null} }`, and the catch deliberately logs nothing (never log ciphertext on a POPIA column). **Do not touch `KEY_SALT`** — `"camp404-pgcrypto-v1"` derives every live key. The five existing `decryptOrNull` call sites (`users.ts:424-425`, `camp-management/actions.ts:152-153`, `mcp/tools/{people.ts:140-142,profile.ts:417-419,reimbursements.ts:95}`) are all the two-state ID/bank case and stay as they are.

**`encryptOrPreserve`** — verified end to end. `getIdDocuments` (`apps/web/lib/users.ts:421-428`) reads with `decryptOrNull`, so unreadable ciphertext renders as a blank form field; `setIdDocuments` (`:415-419`) then calls `idColumnsFor(id.idType, id.idNumber ? encrypt(id.idNumber) : null)`, and `idColumnsFor` (`packages/db/src/id-documents.ts:43-49`) sets the matching column and nulls the *other* one unconditionally. Donor fix, four lines: `const next = safeEncrypt(incoming); if (next !== null) return next; return decryptField(stored).state === "unreadable" ? (stored ?? null) : null;`. Give `idColumnsFor` a `stored` parameter rather than moving the load inside it, so it stays pure and unit-testable. Three write paths need it: `users.ts:415`, `mcp/tools/profile.ts:91-99` (same shape, `if (idNumber)`-guarded so less sharp), and `mcp/tools/profile.ts:452-459` for `eftDetailsEncrypted`, which never routes through `idColumnsFor`. Leave `packages/db/src/maintenance.ts:34` alone — that is the deliberate plaintext→ciphertext backfill.

**schema-invariants test** — pin `ENCRYPTED_COLUMNS` to exactly `["passport_encrypted","sa_id_encrypted","eft_details_encrypted","account_details_encrypted"]`; assert each is `PgText`, assert no plaintext sibling column exists, and guard against a vacuous loop with `expect(TABLES.length).toBeGreaterThan(35)` (Camp 404 has 38 pgTables). One real adaptation: the donor also asserts `notNull === false` ("an unreadable column must be storable as absent"), and `reimbursements.account_details_encrypted` **is** `.notNull()` — which is exactly why `packages/db/src/account.ts:122` scrubs it to `""`. Allowlist that one column as a *documented exception* in the test rather than dropping the assertion. Ride the two MISSED items along in the same file: `predicateText(SQL)` (walks `SQL.queryChunks`/`StringChunk`/`Column` to render a WHERE clause as flat text) pins the predicates of Camp 404's two shipped partial unique indexes (`schema.ts:522-524`, `:571-573`), which matters because `onConflictDoUpdate` against a partial index fails at runtime unless the statement repeats the predicate (`mcp/tools/profile.ts:81-89` is exposed); and the FK sweep walks `config.foreignKeys → getTableConfig(reference.foreignTable).name` against the exported table set, catching a dangling reference before it becomes a migration that only fails against production.

**authorise-before-SELECT** — `getCampMemberDetail` (`packages/db/src/roster.ts:155-200`) selects `passportEncrypted`/`saIdEncrypted` unconditionally and *both* `getMemberDetailAction` (captain, decrypts) and `getPublicMemberProfileAction` (any approved member, discards via `presentPublicMember`) call it. The captain gate runs before the *decrypt* but not before the *select*, so a non-captain's request pulls ID ciphertext into render scope and relies on the projection never serialising it. Fix is the donor's one-liner: `options: { includeIdDocuments: boolean }` and `...(options.includeIdDocuments ? { passportEncrypted: schema.users.passportEncrypted, saIdEncrypted: schema.users.saIdEncrypted } : {})` in the select. Only two columns — `eftDetailsEncrypted` isn't in this query at all — so S is if anything generous. Adopt the donor's returned-shape convention at the same time (`idNumber: string|null` **and** `idUnreadable: boolean` side by side) so the third state has somewhere to land.

**sole-captain guard** — `deleteOwnAccount` (`apps/web/app/profile/actions.ts:55-68`) checks auth, `hasCampAccess`, a typed "DELETE", then erases. No guard of any kind. The donor's three block codes collapse to one for a single camp: `sole_captain`, over `count(users where rank='captain' and sanitised=false) <= 1`. The counting primitive already exists — `getBootstrapState()` returns `captainCount` from `count(*)::int where rank='captain'` (`packages/db/src/bootstrap.ts:21-27`) — but note it does **not** filter `sanitised = false`, which the guard must add. Two donor design properties are worth taking whole even without the grace machine: return **every** block at once with the message the UI renders verbatim ("you shouldn't discover the second one after fixing the first"), and re-check eligibility **at the moment of erasure**, not only at request time — two captains can each pass a request-time guard on different days and both be erased later. This half is shippable today with zero schema change; the grace machine (`DeletionPhase = none|grace|due|cancelled|sanitized`, `now >= graceEndsAt ⇒ "due"`, `canCancelDeletion ⟺ grace`, `cancelDeletionOnSignIn` refusing a `due` request so a login cannot race the sweeper) can follow.
