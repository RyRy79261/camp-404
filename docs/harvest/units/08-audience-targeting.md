# 08 — audience-targeting

**Headline:** Camp 404 already independently built the donor's crown jewel (one pure, injected-row-set resolver shared by both consumers), so the port is everything wrapped *around* it — a live "resolves to N members" count fed by that same resolver, a refusal at zero, and a `scope` field on the announcement compose boundary so the four non-`everyone` scopes finally have a writer.

**Camp 404 today:** `computeAudience(broadcast, data, senderId)` (`packages/db/src/audience.ts:29-64`) is pure, zero-I/O, over the injected seam `AudienceData` (`:13-22`), and is shared verbatim by `resolveAudience` for broadcasts (`packages/db/src/broadcasts.ts:52-90`) and `openActivation` for questionnaires (`packages/db/src/activations.ts:81-90`) — 8 pure unit tests (`apps/web/lib/__tests__/audience.test.ts`) plus 5 PGlite integration cases (`packages/db/src/__tests__/activations.test.ts:30/60/73/86/127`). What is missing is every affordance around it: no recipient-count preview anywhere (four greps: zero hits for `resolvedCount|previewAudience|audienceCount|Resolves to|will receive`), no zero-audience refusal, and `createAnnouncementDraft` still hardcodes `scope: "everyone"` (`broadcasts.ts:168`).

**previewAudienceCount.** `"use server"`, takes the audience, Zod-parses it, re-runs *the same* `gateCaptain()` the send runs, builds the context, calls the *same* `computeAudience`, returns `{ok:true,count} | {ok:false,error}`. Two donor lessons are free and load-bearing. (1) `audience-count.ts:16-32` is a 30-line header recording the real bug: the preview reused a sibling screen's action gated on a different domain, so the preview refused an author while Publish stayed armed. In Camp 404 terms: call `gateCaptain()`, not something looser. (2) `broadcastRefusal` (`audience-count.ts:48-55`) duplicates the publish path's wording deliberately "so the preview refuses in the same words the publish would". The questionnaire-side sibling's test asserts `expect(db.calls).toEqual([])` on a refusal (`questionnaire-actions.test.ts:234`) — a refusal must cost zero DB round-trips, which matters behind a 300 ms debounce. Drop `requireOrgSession({capability, domain})`, the engineer-rank refusal and `editionId` entirely.

Adopt both halves: drop the `blocking = true` filter (letting `nextGate`'s own `if (!action.blocking) continue` at `apps/web/lib/required-actions.ts:32` do the gating), and add the read-time join as belt-and-braces over the existing write-side expiry in `questionnaire-lifecycle.ts`. ## Deliberately skip

- **JSONB `audience` column.** Camp 404's normalised encoding (scope enum + nullable `team` at `schema.ts:549` + targets table at `:578-592`) is queryable and indexable; the donor needed JSONB only because its grammar carries arrays. The donor's own schema is the cautionary tale — `questionnaireScopeEnum` survives at `schema.ts:1305` as a vestigial column no audience path reads.
- **Chunked notification insert.** The donor's justification is a scale argument (10 922 recipients, SQLSTATE 08P01). Camp 404 binds 8 columns × ~80 rows ≈ 640 params against 65 535.
- **`project_roles` / `member_role_assignments` / consent enum / `privileges.tsx` permission editor.** A role system for organisations. Camp 404's two-value `rankEnum` + derived `is_lead` is the right call at this size.

- **`resolveBulletinAudience` wrapper, `shouldSendImmediateEmail`, `NotificationApp`/`resolveNotificationLinkApp`.** No package boundary to bridge (both consumers are in one file), no email channel (`notificationChannelEnum` is `[push, in_app, both]`, `schema.ts:172`), one app.

- **Anti-tests on source text** (`org-rank-enforcement.test.ts:423-440`). Clever, but brittle to renames and Camp 404 has few targeted-notification writers.
