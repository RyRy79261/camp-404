**Skeleton kit.** Nine exports (verified): `Skeleton:31`, `SkeletonRegion:47`, `SkeletonText:68`, `SkeletonHeading:92`, `SkeletonCard:111`, `SkeletonRow:132`, `SkeletonCardGrid:153`, `SkeletonField:172`, `SkeletonForm:182`. The whole file's token surface is `bg-muted` ×2, `bg-card` ×2, `border-border` ×2 — all present in Camp 404 (`globals.css:22`, `:24`, `:29`), so it compiles unchanged. Three properties are what make it worth copying rather than hand-rolling, and its test pins all three: `SkeletonRegion` owns `aria-busy` plus **one** `aria-live="polite"` sr-only label however many bars are inside (`skeleton.test.tsx:49`, `:163` assert `querySelectorAll(".sr-only")` has length 1); every pulse block is `aria-hidden` (`:29`, `:161`); and `SkeletonCardGrid` passes its container className through **byte-for-byte** (`:116` asserts `grid.className).toBe("grid gap-4 sm:grid-cols-2 lg:grid-cols-3")`) — which is the whole point, because the boundary has to hold the destination's exact box. Two chores on the way in: run `pnpm format` (`.prettierrc.json` sets `semi: true`, several existing `packages/ui` components are semicolon-free), and prefix `animate-pulse` with `motion-safe:` to match this repo's existing hygiene.

**Segment-root loading, not 24 bespoke ones.** `apps/org/app/(console)/loading.tsx` is 27 lines and documented as covering "the Overview page and anything below that has not written a closer one", rendering `SkeletonRegion > ConsoleHeadingSkeleton + SkeletonCardGrid`. It also records the payoff: "`<Link>` prefetches a dynamic route down to its nearest loading boundary, so this markup is usually already in the browser before the nav item is clicked." The closer boundary (`status/loading.tsx`, 24 lines) exists only because that page's grid genuinely differs — it reproduces `grid gap-4 lg:grid-cols-3` with a `lg:col-span-2` exactly. Start with a group-level default at `apps/web/app/`, `app/captains/`, `app/captains/questionnaires/`, and add closer ones only where a page's shape is materially different (the roster table is the obvious second).

**Questionnaire completion — port the shape, not the denominator.** Donor, verbatim at `questionnaire-activation.ts:139-141`: `const sent = actions.length; const completed = actions.filter(a => a.status === "completed").length; return { sent, completed, pending: sent - completed };` — with the rationale at `:132-134` that pending/waived/expired all count outstanding. Camp 404's own spec at `docs/questionnaire-builder.md:390` says the opposite: "**completion %** = completed / (pending + completed), excluding waived/expired." Follow the spec. Keep the donor's *shape*: a per-send record `{activationId, title, sent, completed, pending, completionPct}` plus an overall rollup `{sends, totalSent, totalCompleted, completionPct}`, with `=== 0 ? 0 : Math.round((c/s)*100)` at both ratios and `pending` derived as a complement rather than re-counted. Add a third bucket the donor does not have — `closed: waived + expired` — so the excluded tail is visible instead of silently dropped. Substrate is already in place: `questionnaire_activations` (`packages/db/src/schema.ts:537`), `required_actions` with `required_action_status ["pending","completed","waived","expired"]` (`:125-130`), and `packages/db/src/questionnaire-lifecycle.ts:161-162` / `:224-225` already expire rather than delete pending gates *specifically to preserve metrics*. The surface is specified and routed at `docs/questionnaire-builder.md:214` (`/captains/questionnaires/[key]/metrics`) and confirmed unbuilt — no `metrics/` directory under `apps/web/app/captains/questionnaires/[key]/`.

**Month bucketing.** `bucketSubmissionsByMonth(dates)`: filter `!Number.isNaN(d.getTime())` first, return `[]` on empty, tally into a `Map` keyed `` `${d.getUTCFullYear()}-${String(d.getUTCMonth()+1).padStart(2,"0")}` ``, then walk from `Date.UTC(first.getUTCFullYear(), first.getUTCMonth(), 1)` to the last month with `cursor.setUTCMonth(cursor.getUTCMonth()+1)`, gap-filling zeroes, under a `for (let i = 0; i < 120 && ...)` runaway guard. `hasSeries(points)` is `points.length >= 2` — the caller *omits* the chart rather than drawing one. Copy the test with it: it pins two Septembers → one point + `hasSeries` false, Sep + two Decembers → 4 points with Oct/Nov at 0, the year boundary `["2026-11","2026-12","2027-01"]` counts `[1,0,1]`, an invalid Date dropped, and the conservation invariant (total counted === input length).

**Chart.** 100 lines of inline SVG, no `"use client"`, `W=700 H=150`, gridlines at 0.25/0.5/0.75, y-scale `Math.max(1, ...counts)`, x-step `W/(n-1)`, `role="img"` + aria-label at `:46-47`, per-point `<title>` at `:81`, and a readable `<ul>` of label/count pairs underneath so colour is never the only encoding. Exactly three retokens (verified): `var(--color-ab-teal)` at `:61` (polygon fill, opacity 0.14), `:65` (polyline stroke), `:77` (circle fill) → `var(--color-accent)`. `var(--color-border)` (`:57`) and `var(--color-card)` (`:78`) already exist in Camp 404. **It throws on `points=[]`** — `coords[0]!` at `:29` and `points[0]!` at `:31` — so add `if (points.length < 2) return null;` internally rather than trusting every caller to gate.
