# 09 — bulletins-announcements

**Headline:** Camp 404's broadcast *engine* is already ahead of the donor — take two things only: the live "resolves to N members" preview gated on the same check as the write, and the standalone read page whose authorisation IS the delivery row. Those close a live dead-end (every push carries `refType:"announcement"`/`refId` with no route to open) and give the scoped-send work its safety net.

**Camp 404 today:** `broadcasts` + `notification_deliveries` (`packages/db/src/schema.ts:836-880`, `:903-960`) is a strict superset of the donor's `bulletins`/`notifications` — it adds `kind`/`scope`/`team`/`channel`/`presentation`/`send_at`/`dispatched_at`/`ref_type`/`ref_id`, a scheduled-dispatch cron and an FCM drain the donor has none of, and `publishAnnouncement` (`packages/db/src/broadcasts.ts:228-290`) claims the draft with a single-statement compare-and-swap plus `.onConflictDoNothing()` against the partial unique index at `schema.ts:951-958` — a stronger race guard than the donor's `SELECT … FOR UPDATE`. What is genuinely absent: any by-id read of an announcement, any audience control (`ComposeAnnouncementInput` is title+body+presentation only, `packages/types/src/announcement.ts:23-27`; scope is hardcoded `"everyone"` at `broadcasts.ts:172`), any read-rate signal, any pin, and any test over the server/data layer.

**1. Live audience-count preview.** ~20 lines and Camp 404 already owns both halves: `resolveAudience(broadcast, senderId)` (`broadcasts.ts:52-91`) is the *same* function `publishAnnouncement` calls at `:262`, and `requireCaptain()` (`actions.ts:23-40`) is the *same* gate all four writers use. The action is: `requireCaptain()` → parse the audience shape → `resolveAudience({id, scope, team}, captainId)` → `{ok:true, count}`. The donor's file exists *because* it got this wrong: the composer reused the questionnaire preview action, which gated on `{capability:"read", domain:"questionnaires"}` while the publish gated on `bulletins`, so an author lost their recipient count in a refusal naming a screen they were not on — while Publish stayed armed (docblock verbatim at `audience-count.ts:16-32`). Rule to carry: **gate the preview on the same thing you gate the write on; the preview is never the security boundary.** This is not theoretical here — `team_memberships` has **zero production INSERTs** (spot-checked: only `packages/db/src/__tests__/_factories.ts:39` inserts, `packages/db/src/account.ts:96` deletes), so a team-scoped send today resolves to nobody, silently. Do NOT port `buildAudienceContext` (seven unfiltered table reads on every 300 ms debounce tick) or `requireOrgSession`.

**2. The read page, and the rule behind it.** Camp 404 writes `refType:"announcement"`/`refId: broadcast.id` onto every delivery (`broadcasts.ts:279-280`, verified) and copies both into the FCM data payload (`push.ts:97-99`) — and **no route consumes them**: 25 `page.tsx` files, only `notifications/page.tsx` and `captains/announcements/page.tsx` touch this domain. Inbox rows are inert `<li>`s. The donor's read model is the shape to copy exactly (`apps/web/lib/bulletins.ts:29-57`): SELECT the delivery for `(userId, broadcastId) LIMIT 1`; if absent return `null` **without reading the broadcast row at all** (its test pins this — `notifications-inbox.test.ts:202`, "The bulletin itself was never even read."); then read the broadcast and return `null` if `published_at IS NULL` so a guessed draft id leaks nothing. The delivery row *is* the permission — single-tenant-safe by construction, no extra authz. Page structure: `export const dynamic = "force-dynamic"`, `z.string().uuid().safeParse(segment)` → `notFound()` so a bad segment never becomes a query, the app-wide blocking gate runs **before** the read (for Camp 404: the `nextGate` ladder + AcknowledgementGate still outrank it), then back-link/title/date/body. Note this reverses a documented line: `design/spec/surfaces/09-notifications.md:120` currently records "no deep-link" as the inbox's behaviour — ship the spec edit with the route.

**3. Audience on the compose input.** `ComposeAnnouncementInput` is the single narrowest point in the whole pipeline; the DB, `resolveAudience` and `dispatchDueBroadcasts` already support all five scopes. Take the donor's *shape* (one Zod schema is the validation authority; the update action extends it with `id`), not its `AudienceSpec` union. Express it over Camp 404's own enum so an invalid combination is unrepresentable: `{scope:"everyone"} | {scope:"team", team: Team} | {scope:"team_leads"} | {scope:"drivers"} | {scope:"individual", targetUserIds: z.string().uuid().array().min(1)}` — that makes "a team send with no team" a parse error rather than a silent zero-audience. **Do not add `channel` in the same pass**: `design/spec/open-questions.md:126` (D24) / `design/spec/surfaces/15-announcements.md:206` (OQ5) withhold it pending the push UIs. Keep the donor's fewer-forms law as a comment: *a bulletin never collects data; anything needing an answer is a questionnaire.*

**4. `AudienceSelect`.** A dumb `Select` variant that resolves nothing — the parent feeds `resolvedCount` down (`audience-select.tsx:29-31`) and the three-branch copy at `:41-45` renders `Resolves to no {noun} yet` / `Resolves to ~1 {singular}` / `Resolves to ~N {noun}`. Camp 404 has the picker half already (`captains/questionnaires/[key]/send/send-form.tsx:186-197` scope Select, `:201-215` team Select) but no count line anywhere. Retoken the noun to "members". **Do not regress** what send-form already has that the donor lacks: a searchable individual-member multi-select (`:85-100`, `:217+`). Effort M only because it should be wired into both send surfaces plus the new announcement audience picker.

**5. Read rate.** Verbatim from `packages/ui/src/lib/bulletin.ts:19-24`: `total = Math.max(0, Math.floor(of)); opened = Math.min(Math.max(0, Math.floor(read)), total); percent = total === 0 ? 0 : Math.round((opened/total)*100)` → `{read, of, percent}`. Test table ports as-is: `readRate(1,3).percent === 33` (round, not floor), `readRate(0,0) === {0,0,0}`, `readRate(50,30)` clamps to 100. Drop it in `packages/core` (pure, no I/O — the barrel at `packages/core/src/index.ts:32-39` is exactly this kind of module). The DB half is one line: `listAnnouncements` (`broadcasts.ts:129-137`) has correlated `count(*)::int` subqueries for `recipientCount` and `acknowledgedCount` but never tallies `read_at`, which every delivery carries (`schema.ts:929`) and `markRead` maintains — add a third subquery `and nd.read_at is not null`. Then render the donor's bar in `PublishedCard`: `role="progressbar"`, `aria-label="Read rate"`, `h-1.5 bg-muted` track / `bg-primary` fill (`bulletin-card.tsx:97-109`). Note `ProgressBar` (`packages/ui/src/components/progress-bar.tsx:21-22`) clamps only the *percent*, not the numerator, so `readRate` is not redundant with it.
