**Skeleton kit.** Ten exports, `react` + `cn` only, no hooks, server-safe: `Skeleton` (`aria-hidden`, `animate-pulse rounded-md bg-muted`, deliberately no intrinsic size so each route sizes it), `SkeletonRegion` (the root wrapper — `aria-busy="true" aria-live="polite" data-loading="true"` + one `sr-only` `label = "Loading…"`, so one polite announcement per boundary, and `data-loading` is a real Playwright hook), then `SkeletonText`, `SkeletonHeading`, `SkeletonCard`, `SkeletonRow`, `SkeletonCardGrid`, `SkeletonField`, `SkeletonForm`. `--color-muted` exists in Camp 404's `@theme`, so it compiles unchanged. Two edits on landing: wrap the pulse in a `prefers-reduced-motion` guard (WP8 #132 — only `voice/waveform.tsx` honours it today) and run `pnpm format` (donor is semicolon'd, several `@camp404/ui` files are not).

**groupByDay.** Copy `dayKey` alongside — it is module-private: `${getFullYear()}-${pad(getMonth()+1)}-${pad(getDate())}`, local calendar, deliberately not UTC. `groupNotificationsByDay<T extends {createdAt: Date}>(items, now = new Date()): DayGroup<T>[]` where `DayGroup<T> = {key, label, items}`. Yesterday is `new Date(now); setDate(getDate()-1)` — platform handles rollover, which matches MEMORY's date rule. The two most recent days get "Today"/"Yesterday"; everything else keeps the raw `YYYY-MM-DD` as its label. **It does not sort** — single linear pass, opens a group when the key changes, so unsorted input silently yields duplicate groups. Camp 404 is safe only because `listInbox` ends `.orderBy(desc(createdAt))` (`broadcasts.ts:492`); state that as a precondition in the file. Rename to `groupByDay` (it isn't notification-specific), land at `packages/core/src/group-by-day.ts`, add `export * from "./group-by-day"` to `index.ts:39`.

**dayGroupHeading + day-group list.** `dayGroupHeading(label)`: `/^(\d{4})-(\d{2})-(\d{2})$/` — no match → `label.toUpperCase()` (so "Today" → "TODAY"); match → `new Date(y, m-1, d).toLocaleDateString("en-GB", {weekday:"short", day:"numeric", month:"short"}).toUpperCase()` → "MON 20 JUL". 13 lines. Retoken the list, don't lift it: the donor wraps each group in `divide-y divide-border/60 rounded-xl border border-border bg-card/40`, but Camp 404's rows are already individually bordered tinted cards (`notification-row.tsx:43-45`), so the group is a heading over the existing `gap-3` stack. Keep the heading recipe verbatim: `text-[11px] font-bold uppercase tracking-[0.12em] text-muted-foreground`.

**Per-row read (owner call).** Three ideas, all verified in the donor's 67-line row: (a) `const read = item.read || opened` — optimistic state **derived, not seeded**, so a server refresh wins; (b) `if (read && !item.link) return row;` — an already-read linkless row renders as the bare div with **no `<button>` wrapper at all**, which is Camp 404's own "nothing may claim something untrue" rule; (c) `startTransition` + `disabled={pending}`. The action wrapper is Camp 404's own: `markRead(userId, ids)` already exists and takes an array. Two things to take verbatim from `notifications-actions.ts`: the two-path revalidation (`revalidatePath("/notifications")` **plus** `revalidatePath("/", "layout")` — the second is what refreshes the bell) and `unstable_rethrow(err)` **before** building the error string. Do **not** copy `z.string().uuid()` — `apps/web/app/notifications/actions.ts:17-19` documents why (the E2E store uses ids like `test-user-1`).

**Delivery-row-as-permission.** A broadcast body is readable iff a `notification_deliveries` row ties it to this user — receiving it is what makes it readable, so a wrongly-scoped broadcast 404s rather than leaking and there is no second authz system to keep in sync with `resolveAudience` (`broadcasts.ts:52`). Copy the query **ordering**, which is what makes it safe: select the delivery row first, return null if absent, never query the broadcast at all. The donor's test asserts `dbMock.queries.length === 1`; the PGlite harness (`packages/db/src/__tests__/_harness.ts`) can assert the same against real SQL. Second guard: an unpublished draft the user somehow has a row for is still null.
