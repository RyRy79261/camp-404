# 04 — notifications-engine

**Headline:** Camp 404's delivery pipeline beats the donor's, but it has exactly ONE message producer (a captain typing an announcement) — take the donor's pure zero-I/O payload-builder seam plus a `kind` column so lifecycle events can reach an inbox at all.

**Camp 404 today:** Richer than the donor on delivery — `broadcasts` + `broadcast_targets` + `notification_deliveries` + FCM push + scheduled `sendAt` + an acknowledge takeover gate (`packages/db/src/schema.ts:836-961`), with a race-safe transactional publish and `.onConflictDoNothing()` against a real partial unique index (`packages/db/src/broadcasts.ts:228-290`). Poorer on production: I grepped the whole repo and the ONLY two `insert(schema.notificationDeliveries)` sites are `broadcasts.ts:270` and `:360`, both fed by a captain-composed row — so approval decisions, captain promotion, questionnaire sends and the reminders cron produce nothing anyone can see.

**1. Payload-builder seam.** The donor's ten builders are AfrikaBurn nouns and are useless here; the *architecture* is what ports: a pure zero-I/O module returning `NotificationPayload {kind, title, body, link}`, with the DB insert and channel decision left to the caller. Verified correction to the original analysis: **Camp 404 does NOT already have the delivery half.** `notification_deliveries` (schema.ts:903-961) columns are id, broadcastId, userId, title, body, channel, presentation, pushStatus, refType, refId, readAt, acknowledgedAt, deliveredAt, createdAt — no `kind`. `presentation` is a different axis (how it interrupts), and `presentationIcon` (`apps/web/app/notifications/presentation-meta.ts:6-12`) keys off it. Worse, `senderName` comes only via the `broadcasts→users` leftJoin (`broadcasts.ts:486-490`), so a system row with `broadcastId NULL` renders a generic Bell and no attribution — the live open question at `design/spec/surfaces/09-notifications.md:220`. So the port is: pure module + `kind` migration + `InboxItem` projection change + attribution fallback. Derive the TS union from the pgEnum (`(typeof schema.…enumValues)[number]`, the pattern at `broadcasts.ts:29`), never retype it — the donor triplicated its kind list across types/schema/UI with three "keep in sync" comments.

**2. Live audience count.** `send-form.tsx:39` declares `type Scope = "everyone" | "team" | "team_leads" | "individual"` — it omits `drivers`, which `broadcast_scope` supports (schema.ts:168) and `computeAudience` resolves (`packages/db/src/audience.ts:53-55`), so drivers are unreachable from that screen. Worse, `team_memberships` has exactly ONE insert in the repo (`packages/db/src/__tests__/_factories.ts:39` — the test factory), so "A team" and "Team leads" resolve to zero and `toast.success("Sent to members")` fires anyway (`send-form.tsx:118`). Camp 404 already owns both halves of the resolver (pure `computeAudience` audience.ts:29-64, I/O `resolveAudience` broadcasts.ts:52-94), so this is a thin captain-gated preview server action. Copy two mechanics verbatim: the 300ms debounce keyed on the serialised spec with a `cancelled` flag (`bulletin-composer.tsx:96-113`), and the rule that a disabled submit is convenience, never the boundary — the server must refuse or at minimum name a zero audience.

**3. Publish confirm.** Do **not** port `SELECT … FOR UPDATE`. `publishAnnouncement` claims the draft with a conditional UPDATE inside the transaction (`WHERE id=? AND senderId=? AND kind='announcement' AND scope='everyone' AND publishedAt IS NULL RETURNING`, broadcasts.ts:234-247 via `isOwnedAnnouncementDraft` :36-44); under READ COMMITTED the loser blocks on that UPDATE's own row lock, re-evaluates, matches nothing, and is refused. Fan-out is already inside the same transaction (:269-283), which is the donor's one deliberate atomicity exception. Frozen-after-publish is moot — Camp 404 refuses *all* post-publish edits. What's actually missing is the UI: `onClick={() => onPublish(a.id)}` (announcements-manager.tsx:434) with no dialog, in a file that already imports Dialog, and no recall path anywhere in `actions.ts`. Take the principle: an irreversible send confirms, and a refused edit **throws** rather than silently dropping ("a discarded title change would toast 'Bulletin saved' over a title that did not move").

**4. Privacy guard.** 12 lines: join `[title, body ?? "", link ?? ""]` with `\n`, lowercase, `needles.some(n => { const needle = n.trim().toLowerCase(); return needle.length > 0 && haystack.includes(needle); })`. Take the tests too or it isn't a guard: five planted SECRETS (swap for Camp 404's — pgcrypto'd SA ID/passport per AGENTS.md:143-149, `emergency_contacts` jsonb schema.ts:279-282), the non-vacuity test asserting `true` on a payload titled `"Your phone +27821234567 was updated"`, and the blank-needle test. Camp 404's `redactPii`/`sanitizeReportText` do the opposite job (scrub outbound text for the public GitHub tracker) — this is the inbound proof.

**5. Skeletons.** Verified: `find apps -name loading.tsx` returns **0**, and `packages/ui/src/components/` has no Skeleton. `/notifications` is `force-dynamic` (page.tsx:10) and does two sequential DB round trips before paint (:28-32), showing a blank screen for the whole wait. The donor's `skeleton.tsx` (204 lines) is near-drop-in — no hooks, `bg-muted` only, and `SkeletonRegion` owns a single `aria-busy` / `aria-live="polite"` wrapper (:47-65). Obey its stated rule: *"Rows, not cards: the inbox is a list, and a grid of card placeholders would be a lie that reflows the moment the real rows arrive."*

## Already covered in Camp 404
- **Pure audience resolver with multiple consumers** — `computeAudience` (audience.ts:29-64) is pure over injected row sets with THREE consumers (`publishAnnouncement`, `dispatchDueBroadcasts`, `openActivation` activations.ts:81-90), and enforces exclusions the donor has none of: system actors, sanitised accounts, and always the sender (audience.ts:63).
- **The bell** — `TopChrome` (`packages/ui/src/components/top-chrome.tsx:49-65`) has the same 99+ cap, a count-carrying aria-label, an `aria-hidden` badge, hidden at 0, server-rendered count (`app/page.tsx:76`, awaited :86). Nothing to port; see the mount gap below.
- **Inbox row + relative time** — `notification-row.tsx` is a hookless server `<li>` with icon circle, New pill, `<time>`, whitespace-pre-wrap body; `presentation-meta.ts` has an injectable-`now` `formatRelativeTime` with a unit test. The donor ships three drifted copies with three different bucket sets.
- **Owner-scoped reads** — every recipient read pins `userId` server-side (listInbox :491, countUnread :503, getPendingAcknowledgements :423, acknowledgeDelivery :448, markRead :524); `acknowledgeDelivery` additionally pins `presentation='acknowledge'` (:452), a guard the donor lacks.
- **Idempotent fan-out** — partial unique index on (broadcast_id, user_id) WHERE broadcast_id IS NOT NULL (schema.ts:955-960) + `.onConflictDoNothing()`. The donor has no equivalent.
- **Best-effort logging pattern** — `appendMcpAuditLog` (`packages/db/src/mcp.ts:68-91`): body in try/catch, swallowed, "Auditing must never break a tool call."

- **Notification dropdown panel** — dark-only mobile-first at 430px; a full-page inbox is the right answer, and `TopChrome` is deliberately framework-agnostic (plain `<a>`, no `next/*`).
- **Pinned bulletins / BulletinCard / PinnedBulletinBanner** — no `pinned` column, no member-facing announcement list, and a banner would fight the acknowledge gate for the same screen.
- **`plainPreview` markdown stripper, email transport, day grouping** — no markdown (bodies are plain text, `whitespace-pre-wrap`, "No markdown rendering"); no email channel (`notification_channel` is [push, in_app, both]); day headers are not design-mandated (the board uses relative strings).

## DB changes this unit implies
- `notification_deliveries.kind` — new pgEnum (or reuse/extend `broadcast_kind`), NOT NULL with a backfill default, so a `broadcastId NULL` system row carries a class. **Required by the builder seam.**
- `CREATE INDEX notification_deliveries_user_created_idx ON notification_deliveries (user_id, created_at DESC NULLS LAST)` — `listInbox` orders `desc(createdAt)` with nothing to serve it.
- A per-user "last reminded at" marker (column on `users`, or an append-only table) for the reminders/digest max-1-per-day cap. Same missing piece the donor names in its own stub.
- Nothing else. No `pinned`, no `link` (refType/refId is the structured equivalent), no `security_events`, no `origin`.

## Corrections applied
- **"Camp 404 already has the delivery half"** (item 2) — false. No `kind` column, and `senderName` is only reachable through the broadcasts join, so a system row has no attribution. Effort is M–L, not M.
- **`notification_deliveries` is a "strict superset" of the donor's `notifications`** (item 12) — false, and that word was load-bearing for the ALREADY_HAVE. The donor carries `kind` and `link` with no Camp 404 counterpart. What holds is the index gap.
- **"Derive the TS kind union from the pgEnum"** (item 11) — the pattern is real (`broadcasts.ts:29`) but `broadcast_kind` lives on `broadcasts`, not on `notification_deliveries`; deriving the type is free, making it reach the inbox row needs the migration.
- **"Camp 404 writes no best-effort log"** (item 15) — false. `appendMcpAuditLog` (`packages/db/src/mcp.ts:68-91`) is exactly the donor's shape, already shipped. Verdict PARTIAL; only IP/user-agent capture and a second call site are missing, so the port is cheaper.
- **"Camp 404 has no side-write hooks at all"** (item 38) — same correction. The rule half is an extension of an in-repo convention, not an import.
- **"Camp 404 has NO bell anywhere"** (harvest §1) — false; `TopChrome` has one. The real finding is a *mount* gap: one call site.
- **21 functions, not 19**, in `security-notifications.ts`; and the "Camp 404 doesn't own these events" rationale is true for password/email/session but not for account deletion.
- **`publishAnnouncement` needs `FOR UPDATE`** (harvest §1 table) — false. The conditional-UPDATE claim already serialises racers under READ COMMITTED; the gap is a UI confirm and a recall path.
- **Donor's own defects, do not copy:** `shouldSendImmediateEmail("wrangler")` makes a whole email block dead code (`apps/org/lib/actions/wranglers.ts:118`); the insert-chunk doc comment (8 cols / 8191 rows) contradicts the inline one (6 / 10923) — the inline one is stale; the org `mark-all-read-button.tsx` fork silently lost its success toast.
- Minor line drift throughout the digest (page.tsx:28-32 not :31-37; senderId schema.ts:840-842; dispatch refType/refId :369-370; donor `finalize()` :98-100). Immaterial.
