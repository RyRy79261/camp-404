# 16 — registration-state-machine

**Headline:** The donor's 7-state registration machine is dead weight for one camp — but the *writer discipline* around it (compare-and-set on the approval decision, a reason, a notification, one `withTransaction` wrapper) closes Camp 404's single genuine open defect and 15 sites of boilerplate.

**Camp 404 today:** The whole vetting workflow is `approval_status` `[pending, approved, rejected]` (`packages/db/src/schema.ts:50-54`), decided one-shot by `decideApprovalAction` (`apps/web/app/captains/camp-management/actions.ts:216-236`) → `decideUserApproval` (`apps/web/lib/users.ts:261-268`) → `setUserApproval` (`packages/db/src/burner-profile.ts:69-84`), which is an unguarded `UPDATE ... WHERE id = ?` with no `.returning()`, no reason column and no notification. The hard-gate spine (`nextGate` at `apps/web/lib/required-actions.ts:9-38`, three call sites) is the asset the donor *took from Camp 404* — its own header says "ported 1:1 from Camp 404" (`packages/core/src/questionnaire-engine.ts:1-2`).

### 1. The approval TOCTOU guard — the defect

`setUserApproval` sets `{approvalStatus, approvalDecidedByUserId, approvalDecidedAt, updatedAt}` `.where(eq(users.id, userId))`. No status precondition, no `.returning()`. `decideApprovalAction` returns `{ok:true}` unconditionally at `:235`. Two captains on the same roster row decide opposite ways and the second silently wins; a captain acting on an hour-old page overwrites a decision they never saw. Donor fix (`registration-store.ts:644-655`): guard the WHERE on `and(eq(id, userId), eq(approvalStatus, expected))`, take `.returning()`, treat zero rows as a reported failure with one shared sentence — *"This member's status changed since you opened it — reload and try again."* `ApprovalDecisionResult` already has somewhere to put it. **Two extras nobody flagged:** (a) `decideApprovalAction` is the only action in that file that skips `UserId.safeParse` (compare `:202` and `:253`) — a raw client id goes straight to the write; (b) the write goes through the real/test backend split in `users.ts:261`, so the test backend needs the same guard or the e2e stops matching production.

### 2. `withTransaction` — the missed quick win, and it's bigger than reported

Donor `apps/web/lib/db.ts:25-44` is 12 lines: open `createPooledDb()`, `await pooled.transaction(fn)`, `await pool.end()` in a `finally`, plus an exported `Tx` type and a docstring stating the policy ("the ONLY transactional path… reads stay on `db()`"). Camp 404 hand-rolls `const { db, pool } = createPooledDb(); try { … } finally { await pool.end(); }` at **15** sites, not the 4 the digest claims: `maintenance.ts:19`, `camp-config.ts:187`, `activations.ts:92,311`, `account.ts:56`, `questionnaire-lifecycle.ts:125,177,232,331`, `push.ts:172`, `bootstrap.ts:59`, `broadcasts.ts:232,337`, `apps/web/lib/mcp/oauth.ts:163,247`. Put it in `packages/db/src/index.ts` (not `apps/web/lib`) since 13 of the 15 live there. AGENTS.md:85-89 already states the policy the docstring encodes. Items 1 and 3 both need a transaction; this makes each a one-liner.

### 3. Reason + notification

Migration: one nullable `approval_decision_reason text` on `users` (today it carries only `approvalStatus` `:295`, `approvalDecidedByUserId` `:298`, `approvalDecidedAt` `:302`). Donor assembly: reason **required** for the negative decision with a decision-specific sentence, `z.string().trim().max(2000)`, status + reason in one transaction with the guard from item 1, zero rows **throws inside** the transaction so no stale audit row survives, notification fired **after commit** inside try/catch so a failed send can never roll back a decision. Carry the donor's `decision_reason` invariant from day one — a reason written about state X is cleared the instant the row leaves X (`registration-store.ts:630-639`); their repair migration `0027` exists because they retrofitted it. **Sizing correction:** the digest calls the notification "wiring, not construction". Half true. `broadcast_scope` includes `individual` (`schema.ts:169`), `broadcastTargets` exists and `resolveAudience` reads it (`broadcasts.ts:76-80`) — but `createAnnouncementDraft` hardcodes `scope: "everyone"` (`broadcasts.ts:167`) and takes no targets, so you need a small new writer (insert broadcast scope=individual + one `broadcast_targets` row + publish), not an existing call. Without item 3's reason column, a rejection notification is barely better than the current silence — ship them together. Today the applicant reads *"reach out to whoever invited you"* (`apps/web/app/pending-approval/page.tsx:64-69`) and that is all they ever get.

AND status='pending'` (`:246-254`); `unpublishDefinition` cascades identically (`:203-212`) and re-selects open activations *inside* the tx (`:185-188`) to catch a racing send. `getPendingRequiredActions` filters `status='pending'` (`activations.ts:228`) so an expired row never gates. ## Deliberately skip

- **Editions.** `required_actions` has no `edition_id` and its unique index is `(user_id, action_key)` (`schema.ts:679-682`). Drop `editionId` from every donor signature. - **`countWords`/`wordsRemaining`** — only if a word-limited question kind is actually wanted; it isn't in the 16-literal union today.

## Corrections applied

- **REFUTED, and it was the digest's headline:** "closing an activation strands recipients on a dead-end 'form is closed' card forever." **False.** Verified in source: `closeActivation` (`questionnaire-lifecycle.ts:228-256`) expires the pending rows inside a pooled transaction; `getPendingRequiredActions` filters `status='pending'`. The claimed dead end cannot occur. That was the donor's own bug, transplanted unverified. Camp 404's write-side fix is arguably stronger than the donor's read-side LEFT JOIN — the donor's only wins for *reopening* an activation, which `activation_status [draft, open, closed]` doesn't support anyway. **Verdict → ALREADY_HAVE, value low.**
- **REFUTED:** "Camp 404 has no compare-and-set convention, five racy sites." **False.** `captain-promotion.ts:129-141` and both lifecycle writers already do it correctly. Only `setUserApproval` is unguarded. It is one fix plus an AGENTS.md line, not a repo-wide sweep.
- **REFUTED:** the field-kit a11y claim ("labels point at non-labelable elements"). **False.** `question.tsx:95-100` builds `ariaLabel` for exactly this case with a comment saying so. Only the `NumberField` parse-guard and the word-limit `aria-live` counter survive, both low value.
- **REFUTED:** "`&& authUser.primaryEmailVerified` is a one-line change." No such field exists — `AuthenticatedUser` is `{id, primaryEmail, displayName}` (`apps/web/lib/auth.ts:13-17`) and `SessionUser` (`:27`) reads no verified flag from Neon Auth. Landing it means plumbing a new field through the session payload, `AuthenticatedUser`, and `apps/web/lib/test-store.ts`, plus confirming Neon Auth exposes it. **Effort M, not S.** The security argument stands.
- **REFUTED:** "`createInviteAction` availability check doesn't run the save path's validator." **False** — both call `isSyntacticallyValidCode` and both lowercase. The real divergence is check-vs-**redeem** (`claimInviteCode` only trims, `access-control.ts:46`), which is DEFERRED.md:66's known bug, and DEFERRED.md says the fix is *not* small (coordinated change across env + seeds + CI `INVITE_CODES` + e2e fixtures; an earlier partial attempt was reverted).
- **REFUTED:** the donor's `revokeInvite` is "directly copyable, returns a row count, scoped to the creator." It returns `Promise<void>`, is scoped to the **group**, and revokes by stamping `usedAt` — it has no `revoked_at` column, so a donor-revoked invite is indistinguishable from a spent one. Camp 404's dedicated `revokedAt` is the better model; only the `isNull` guard idiom transfers.
- **REFUTED:** "breaking edits to a published questionnaire are silently allowed." `assertCanEdit` (`captains/questionnaires/actions.ts:92-106`) documents the opposite: editing a published head is the deliberate re-version flow, and `publishDefinition` classifies the change and mints a new version. Only the announcement-publish-with-no-confirm candidate survives.
- **Corrected sizing:** `withTransaction` covers **15** hand-rolled sites, not 4 — verified by grep.
- **Corrected sizing:** the decision notification is not "one call" — `createAnnouncementDraft` hardcodes `scope:"everyone"` and takes no targets; a small new writer is needed.
- **Corrected attribution:** required-action fan-out is `openActivation` (`activations.ts:40-125`, `onConflictDoUpdate` at `:116-120`), not `sendActivation`.
