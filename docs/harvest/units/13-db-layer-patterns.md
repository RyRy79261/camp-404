### 1. The limiter (spot-checked, both sides, holds exactly)

Table is three columns: `key TEXT PRIMARY KEY`, `count INTEGER NOT NULL`, `window_start BIGINT NOT NULL` (epoch millis, the window's **start**, never moved while a window is open), plus `index("action_rate_limit_window_start_idx").on(windowStart)` so the sweep is not a seq scan. **`bigint("window_start", { mode: "number" })` — the `mode` is load-bearing**; without it drizzle returns a string and `window_start < ${cutoff}` silently compares strings. Camp 404's `schema.ts` imports no `bigint` today (verified: 0 hits) — add the import.

The whole limiter is one statement: `WITH swept AS (DELETE FROM action_rate_limit WHERE window_start < ${staleCutoff} AND key <> ${key}) INSERT … ON CONFLICT (key) DO UPDATE SET count = CASE WHEN window_start < ${windowStartCutoff} THEN 1 ELSE count + 1 END, window_start = CASE WHEN … THEN ${nowMs} ELSE window_start END RETURNING count, window_start`. The `AND key <> ${key}` matters: a CTE delete and the INSERT share one snapshot, so deleting the row you then conflict on touches the same tuple twice in one command. `STALE_ROW_HORIZON_MS = 24*60*60*1000` — deliberately two orders of magnitude past the longest window, because the sweep uses the *caller's* clock and a tight horizon would let a short-window caller delete a long-window caller's live counter.

Port mechanics, verified against `apps/web/lib/rate-limit.ts`: the seam is `interface RateLimiter { limit(key, opts): RateLimitResult | Promise<RateLimitResult> }` at :73-78, and `limit` is *already allowed to be async* — so a DB-backed implementation drops in behind `rateLimiter` (:81) with **zero call-site changes** across the seven consumers. Adapt the shapes: donor `{key, max, windowSeconds}` → Camp 404 `(key, {limit, windowMs})`, and donor `{allowed, retryAfterSeconds}` → Camp 404 `{ok, retryAfterSeconds}`. Keep verbatim: the `count <= max` boundary (3rd attempt passes, 4th refused), `Math.max(1, …)`, the fail-**open** `console.error` on storage throw ("a limiter outage would turn into a hard outage of password reset rather than into abuse"), the `if (!process.env.DATABASE_URL) return ALLOWED` guard, and the `Array.isArray(rows) ? rows[0] : rows.rows?.[0]` dual-shape read. That last one is real: **Camp 404 has zero `.execute()` call sites today** (verified), so this is the first place neon-http's bare array and neon-serverless's `{rows}` differ. Ship the donor's `rate-limit.test.ts` with it — its `vi.hoisted` mock of `createHttpDb` and `httpRows()` helper are the only way to exercise both shapes. Take the donor's duck-typed `headers: {get(name): string|null}` parameter for `getClientIp` (more testable than `Headers`); keep Camp 404's name.
