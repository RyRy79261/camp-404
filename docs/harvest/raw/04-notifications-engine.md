## 1. Purpose — what this subsystem actually is

The donor's notification engine is **one `notifications` table read as a per-account inbox by three apps**, fed by two origins:

1. **Personal event notifications** — generated by actions that already exist (registration decision, wrangler assignment, officer assignment/acceptance, questionnaire release, supplier standing/step confirmations, account security events). No new data collection.
2. **`bulletins`** — org-authored markdown broadcasts to an **audience**, which fan out at publish time into one `notifications` row per resolved recipient.

The architectural spine is unusually clean and is the reason this unit is worth harvesting:

- **All message text is produced by pure builder functions in `@quagga/core`** (`packages/core/src/notifications.ts`, `security-notifications.ts`). Zero I/O, zero env, zero DB. Each builder takes already-safe display facts and returns a `NotificationPayload {kind, title, body, link}`.
- **The DB insert is a separate, dumb, chunked writer** (`insertNotifications`) that lives per-app.
- **Audience resolution is a single pure function** (`resolveAudience` in `packages/core/src/audience.ts`) with **two consumers**: questionnaire activation and bulletin publish. The bulletin path is a one-line wrapper (`resolveBulletinAudience`) that exists purely to make the call site read intentionally.
- **Email is a courtesy nudge, never the delivery.** In-app is the source of truth. `shouldSendImmediateEmail` is a 4-line pure predicate; the digest is an explicit, self-documenting **stub**.
- **There is no push, no service worker, no websocket, no polling.** Verified: `rg -i 'web-push|firebase|serviceWorker|EventSource|websocket|poll'` across `apps/` + `packages/` returns only Neon driver hits. The only Vercel cron in the repo is the account-deletion sweep (`apps/web/vercel.json` — `/api/account/deletion-sweep`, `0 3 * * *`).

### Why this matters to Camp 404

Camp 404 already has a *richer* delivery layer than the donor: `broadcasts` + `broadcast_targets` + `notification_deliveries` + `push_tokens`, a dispatch cron, a push cron, FCM, scheduled `sendAt`, `presentation: acknowledge|popup|feed`, and an acknowledgement takeover gate. The donor has **none** of that.

What the donor has that Camp 404 does **not**:

| Donor asset | Camp 404 today |
|---|---|

### 3.5 Read/unread model

- **Unread ⇔ `read_at IS NULL`.** Pure mirror `isUnread(n) => n.readAt === null` (`notifications.ts:357-359`) exists **specifically so the SQL predicate and the definition cannot drift** (`:352-356`). `countUnread` at `:362-366`.
- The real query: `count(*)::int` with `and(eq(userId), isNull(readAt))` — `apps/web/lib/notifications.ts:32-41`.
- Marking read is **idempotent + scoped**: `WHERE id = ? AND user_id = <session> AND read_at IS NULL` (`apps/web/lib/notifications-actions.ts:30-36`). A forged id from another account silently no-ops.
- Mark-all: `WHERE user_id = <session> AND read_at IS NULL` (`:60-65`).
- Both revalidate `"/notifications"` **and** `revalidatePath("/", "layout")` so the header badge updates (`:37-38`, `:66-67`).
- **Optimistic client clear**: `notification-row.tsx:30-31` — `const [opened, setOpened] = useState(false); const read = item.read || opened;` — derived, not seeded, so a server refresh still wins.

### 3.9 Dedupe / idempotency

There is **no `(broadcast_id, user_id)` unique index** as Camp 404 has. Idempotency is achieved differently and in exactly two places:

1. **`SELECT … FOR UPDATE` row lock at publish.** Both `saveBulletin`'s update path (`apps/org/lib/actions/bulletins.ts:149-159`) and `publishBulletin` (`:310-319`) take a row lock before reading `published_at`, then refuse if already set. The comment at `:301-309` records the incident verbatim: *"two publishes racing the same draft … both read `published_at IS NULL`, both passed, and both fanned out — the whole audience got the notice twice."*
2. **Audience `finalize()` de-dupes user ids** so a person matched by two selectors gets one row (`audience.ts:99-101`).

Nothing prevents a *deliberate* re-fan-out; the publish action just refuses to re-publish.

### 3.10 Preference / opt-out model — **THERE IS NONE**

Verified by exhaustive grep: there is **no `notification_preferences` table, no per-kind mute, no channel toggle, no unsubscribe**. Every account receives everything targeted at them. The only "opt-out"-shaped mechanism in the whole subsystem is **officer role consent** — an officer assignment with `consent !== "accepted"` never resolves into an audience (`audience.ts:219`, `:253`), which the donor treats as a privacy boundary, not a preference.

This is a deliberate simplicity, and it is the right default for Camp 404's 30–80 users too.

### 3.11 Provenance: `origin` and `link_app`

Two nullable TEXT columns added by migration 0021.

**`origin`** — `NotificationOrigin = "org" | "camp" | "system"` (`notifications.ts:220`). Answers *who sent it*. Values in use: `"org"` (console writes), `"camp"` (a camp lead released a questionnaire — `apps/web/lib/questionnaire-store.ts:282`), `"system"` (security events — `apps/web/lib/account-actions.ts:140-142`; deletion cancel — `packages/db/src/deletion.ts:181`).

**`link_app`** — `NotificationApp = "web" | "org" | "suppliers"` (`notifications.ts:230`). Answers *where the link resolves*. Deliberately a **different axis** from origin: *"the org console writes the supplier inbox, so those rows are sent by `org` and read in `suppliers`"* (`:225-229`).

Two pure helpers:
- `resolveNotificationLinkApp(linkApp, writingApp)` (`:259-264`): `linkApp === undefined ? writingApp : linkApp`. **The whole point is that `??` cannot distinguish "not provided" from "deliberately null"** — the 18-line comment at `:241-258` records the exact bug: `null ?? "org"` stamped every bulletin for the org app, `notificationLinkIsLocal("org","web")` then returned false, the link was dropped, and *"a burner received an AfrikaBurn bulletin and could not open it."*
- `notificationLinkIsLocal(linkApp, thisApp)` (`:274-279`): `!linkApp || linkApp === thisApp`. A null (pre-migration) row counts as local.

### 3.12 Read-rate telemetry

`packages/ui/src/lib/bulletin.ts:19-24`:
```ts
export function readRate(read: number, of: number): ReadRate {
  const total = Math.max(0, Math.floor(of));
  const opened = Math.min(Math.max(0, Math.floor(read)), total);
  const percent = total === 0 ? 0 : Math.round((opened / total) * 100);
  return { read: opened, of: total, percent };
}
```
Clamped so a stale count can never render >100% or negative.

The SQL that feeds it, `apps/org/lib/bulletins.ts:73-84` (list) and `:112-123` (single):
```sql
count(*)::int                                                   AS sent
count(*) filter (where read_at is not null)::int                AS read
-- FROM notifications WHERE kind = 'bulletin' [AND bulletin_id = $1] GROUP BY bulletin_id
```
`getBulletin` was refactored from a filter over `listBulletins()` — the comment at `:89-98` records that *"opening ONE bulletin fetched every bulletin row in the deployment — bodies included, which are up to 20 000 characters each."*

## 6. Validation + edge-case rules, digit-exact

### 6.1 Insert chunking

`NOTIFICATION_INSERT_CHUNK = 1000` — declared **three times** (`apps/web/lib/notifications.ts:126`, `apps/org/lib/notifications.ts:113`, `apps/suppliers/lib/notifications.ts:103`).

Doc comment (`apps/web/lib/notifications.ts:124-125`): *"Rows per INSERT. **Eight** bound columns each, so Postgres' **65535**-parameter ceiling lands at **8191** rows — **1000** keeps a wide margin."*

Inline comment (`:139-143`): *"CHUNKED. **Six** bound parameters per row against Postgres' 65535-parameter ceiling means a single insert dies at **10923** rows with SQLSTATE **08P01** — and because a bulletin publish wraps this in a transaction, the whole broadcast rolled back."*

⚠️ **These two comments contradict each other and only one can be right.** The insert binds 8 columns (`userId, kind, title, body, link, origin, linkApp, bulletinId` — `:147-160`), so the doc comment is current and the inline one is stale from before migration 0021 added `origin`/`link_app`. This is a live instance of the donor's own "comments that lie" audit finding. Do **not** copy the six/10923 numbers.

### 6.2 Query limits

- `listNotificationGroups` → `.limit(200)` (`apps/web/lib/notifications.ts:77`, org `:92`, suppliers `:82`).
- `recentNotifications` default `limit = 6` (`:98` / org `:99` / suppliers `:89`); called with `6` from the panel action (`apps/web/app/(app)/notifications/actions.ts:18`).
- `listSecurityEvents` default `limit = 10` (`packages/auth/src/account.ts:248-251`).
- `NotificationBell` badge cap `max = 99`, renders `"99+"` past it (`notification-bell.tsx:20-22`).

### 6.3 Compose validation

- `title`: `.trim().min(1, "Give the bulletin a title.").max(200)`.
- `bodyMd`: `.trim().min(1, "Write the bulletin body.").max(20000)`.
- Composer `<Input maxLength={200}>` (`bulletin-composer.tsx:184`).
- `plainPreview(markdown, max = 220)` default (`preview-text.ts:20`); the org **list** uses the default, the **composer preview** passes `180` (`bulletin-composer.tsx:168`).
- Audience count debounce: `setTimeout(…, 300)` (`bulletin-composer.tsx:109`).
- Registration decision `reason`: `z.string().trim().max(2000).optional()` (`apps/org/lib/actions/registrations.ts` `DecideInput`), and `request_changes`/`reject` **require** a non-empty reason.

### 6.4 The blocking-questionnaire wire format

`BLOCKING_MARKER = "REQUIRED, blocks registration"` (`apps/web/components/notifications/format.ts:105`).

```ts
export function isBlockingNotification(input: { kind: NotificationKind; title: string }): boolean {
  return input.kind === "questionnaire" && input.title.includes(BLOCKING_MARKER);
}
```
The stored row carries **no separate blocking flag** — the phrase in the title IS the format (`:99-104`). `NotificationItem` then requires `blocking && kind === "questionnaire"` before flagging (`notification-item.tsx:87`) and renders `Required · blocks registration` in destructive colour (`:126-130`).

This is fragile-by-design and the donor says so. **Camp 404 should not copy it** — Camp 404 already has `broadcast_presentation` and `required_actions.blocking` as real columns.

### 6.5 Frozen-after-publish

`PUBLISHED_FROZEN_MESSAGE` (`apps/org/lib/actions/bulletins.ts:100-101`) verbatim:
> "This bulletin has already gone out. Its title and audience are fixed — recipients' notifications carry the title it was sent with, and a broadcast cannot be re-aimed afterwards. Correct the body here, or send a new bulletin."

Rules encoded at `:166-189`:
- If already published **and** (`title !== existing.title` **or** `audienceKey(input.audience) !== audienceKey(existing.audience)`) → **throw**, do not silently drop. The comment at `:166-169` says why: *"the composer posts the whole form back, so a discarded title change would toast 'Bulletin saved.' over a title that did not move."*
- `bodyMd` and `pinned` stay editable after publish.
- `publishedAt` is set only on the `input.publish && !alreadyPublished` transition; *"never un-publish or restamp"* (`:185-186`).

`audienceKey(spec)` (`:76-88`) is **order-insensitive** on selector arrays: `["a","b"]` and `["b","a"]` reach the same people and must not read as a change. Keys:
```
org_outbound:<sorted selectors joined by ",">
org_officer:<sorted officerKeys joined by ",">
project:<groupId>:<mode>:<sorted roleIds joined by ",">
org_internal | org_suppliers   (the bare kind)
```

### 6.6 Capability gating on the write path

`saveBulletin` (`:117-128`) reads the **raw** `id` before Zod parse to choose the capability:
```ts
const isUpdate = typeof (raw as { id?: unknown } | null)?.id === "string";
const session = await requireOrgSession({ capability: isUpdate ? "update" : "create", domain: "bulletins" });
```
The comment records the defect: *"Both paths used to ask for `update`, which meant a role holding only `update` … could compose a brand-new bulletin and broadcast it in AfrikaBurn's name without ever holding `create`."*

Second gate, `assertOrgAudience` (`:43-56`): project audiences are refused outright (*"Bulletins broadcast to org audiences, not a single camp."*), then `canActivateAudience` must pass. `broadcastRefusal` (`:60-64`) names the actor's rank so the refusal reads as a rule:
> "Engineer accounts don't broadcast to burners in AfrikaBurn's name — ask org staff to send it."

`publishBulletin` **re-checks the stored audience** at publish time (`:320-330`), not just at compose.

### 6.7 Bulletin read authorization — the notification row IS the ACL

`getBulletinForCurrentUser` (`apps/web/lib/bulletins.ts:25-58`) and `getBulletinForSupplier` (`apps/suppliers/lib/notifications.ts:161-193`) both:
1. `SELECT id FROM notifications WHERE user_id = <session> AND bulletin_id = <id> LIMIT 1` → null if absent.
2. Then fetch the bulletin; return null if `publishedAt === null`.

So an `org_internal` broadcast, or any bulletin you weren't targeted by, **404s rather than leaking**. There is no separate permission check.

`getPinnedBulletinsForCurrentUser` uses an inner join on the same predicate and then **filters unpublished rows in JS after the query** (`bulletins.ts:92`) — a small inefficiency the tests explicitly cover.

### 6.8 Env-less degradation (the donor's hard rule #4)

Every read returns its empty value rather than throwing:
- `getUnreadNotificationCount` → `0` when `!isDatabaseConfigured()` or signed out (`apps/web/lib/notifications.ts:29-31`), and `row?.count ?? 0` guards a missing aggregate row (`:41`).
- `listNotificationGroups` / `recentNotifications` → `[]`.
- `getBulletinForCurrentUser` → `null`.
- `sendEmail` with no `RESEND_API_KEY` logs to console and returns `{ok: true, id: null, delivered: false}` (`email.ts:58-65`).
- `listSecurityEvents` catches read failures and returns `[]` — *"A failed read must degrade the card, never break the security page"* (`packages/auth/src/account.ts:66-69`).

### 6.9 Best-effort writes (never roll back the primary action)

Every notification/security-log write in the donor is wrapped and swallowed:
- `recordSecurityEvent` — `try {…} catch { /* The change already happened; the log is a record, never a gate. */ }` (`apps/web/lib/account-actions.ts:119-130`; `packages/auth/src/account.ts:224-233`).
- `notifySecurity` — separate try/catch for the inbox row and the email (`account-actions.ts:135-153`).
- The registration decision hook, wrangler hook and questionnaire release hook each wrap the whole notification block and `console.error("[notifications] … hook failed", err)` (`apps/org/lib/actions/registrations.ts:100-102`; `wranglers.ts:136-138`; `questionnaires/actions.ts:504-506`).
- The questionnaire release hook fires **AFTER commit**, outside the transaction: *"Thin + best-effort, AFTER commit — never blocks or rolls back the send"* (`questionnaires/actions.ts:439-441`).
- `deletion.ts:183-196` — two separate try/catch blocks for the inbox row and the security-event row.

Contrast: the **bulletin fan-out is INSIDE the transaction** with the publish stamp and the audit row — *"a published bulletin must never exist without its recipients' notifications, nor notifications without the published row"* (`bulletins.ts:139-141`).

### 6.10 Email: one recipient per message (POPIA)

`apps/web/lib/email.ts:36-45`, verbatim rationale:
> "ONE RECIPIENT PER MESSAGE, ALWAYS. A `to` array used to be handed to Resend verbatim, which puts every address in the `To:` header — so a camp-roster questionnaire send disclosed every member's email address to every other member. That is a POPIA disclosure, not a formatting detail. … **There is deliberately no bcc path**: bcc would still put all of them in one message, one misconfigured header away from the same leak."

Constants: `RESEND_ENDPOINT = "https://api.resend.com/emails"`, `RESEND_BATCH_ENDPOINT = "https://api.resend.com/emails/batch"`, `RESEND_BATCH_MAX = 100` (*"Resend's documented ceiling for one batch call"*), `DEFAULT_FROM = "AfrikaBurn Contributors <no-reply@contributors.afrikaburn.com>"` (`:8-13`).

Behaviour: 1 recipient → single endpoint; N → batch endpoint in chunks of 100; **a failed chunk fails the whole send** rather than reporting partial success (`:81-92`). HTML derived as `<pre>${escapeHtml(text)}</pre>` when not supplied (`:67`).

### 6.11 `maskEmail`

```ts
const at = email.lastIndexOf("@");        // LAST @, so a local part containing one can't confuse it
if (at <= 0) return "…";                  // degrade safely, never echo a malformed address
return `${first}…${domain}`;              // alice@example.com → a…@example.com
```
(`security-notifications.ts:161-168`.) Tests at `security-notifications.test.ts:172-186`.

### 6.12 Relative-time thresholds (three near-copies)

`apps/web/components/notifications/format.ts:19-34`:
`< 1min` → `"Just now"`; `< 1h` → `"N minute(s) ago"`; `< 24h` → `"N hour(s) ago"`; `< 7d` → `en-GB` weekday short; else `en-GB` `{day:"numeric", month:"short"}`.

`apps/suppliers/components/notifications/format.ts:19-34` — **same, plus** a `< 2 * DAY → "Yesterday"` branch at `:30` that apps/web lacks.

`apps/org/components/notifications/relative-time.ts:11-30` — **different again**: adds `days === 1 → "Yesterday"`, `days < 30 → "N days ago"`, else `en-ZA` `{day:"2-digit", month:"short", year:"numeric"}`.

Three copies, three behaviours. Camp 404 should ship exactly one.

### 6.13 Source-label honesty rule

`sourceLabel(kind, origin)` (`apps/web/components/notifications/format.ts:71-78`):
```ts
if (origin === "org") return "AfrikaBurn";
if (origin === "camp" || origin === "system") return null;
return ALWAYS_ORG_SOURCED.has(kind) ? "AfrikaBurn" : null;
```
`ALWAYS_ORG_SOURCED = new Set(["bulletin", "registration", "wrangler", "supplier"])` (`:44-50`). `questionnaire` is **deliberately absent** because it has two possible senders.

The 11-line comment at `:59-69` records the bug: *"a burner's inbox showed '2 hours ago · AfrikaBurn' directly under a headline naming their own camp lead. The meta line contradicted the title and credited a camp's form to AfrikaBurn."* And the rule: **with no origin recorded, say nothing rather than guess.**

⚠️ Note the honesty gap the donor documents on itself (`format.ts:147-154`): `listNotificationGroups` / `recentNotifications` in `apps/web/lib/notifications.ts` **do not project `origin` into `NotificationView`**, so the fallback path is what actually runs today. `apps/org` does project it? No — verified, neither does. This is a shipped-but-unwired feature.

## 7. UX behaviours worth stealing

1. **Lazy panel load.** The header dropdown fetches items only on open via a server action, keyed on `[open, nonce]`, with a `cancelled` guard (`notification-panel.tsx:41-50`). The badge count still comes from the server render so it's correct before any interaction (`:26-28`).
2. **Non-modal Popover, not Dialog.** The comment at `:20-24` argues it explicitly: no page overlay, page behind stays interactive, still gets focus management + Escape + outside-click, `align="end" sideOffset={8}`, collision-avoids on small screens.
3. **Panel sizing** `w-[min(26rem,calc(100vw-1rem))]`, list `max-h-[60vh] overflow-y-auto` (`:30-32`, `:74`).
4. **Filter state lives in the URL** (`?filter=`), each tab is a `<Link>` via Radix `asChild`, so the list stays a server render and a filtered inbox is back-button-friendly. Empty `TabsContent` panels exist purely so every trigger's `aria-controls` resolves (`filter-tabs.tsx:10-14`, `:54-56`).
5. **Zod at the boundary with a soft fallback**: an unknown `?filter=` falls back to `"all"` rather than throwing, *"a shared link with a stale param should still open the inbox"* (`(app)/notifications/page.tsx:66-70`). The org page uses `NotificationFilter.catch("all").parse(...)` (`page.tsx:44`).

### 11.1 `resolveNotificationLinkApp` — the `??` bug that shipped three times

`packages/core/src/notifications.ts:241-279`

```ts
/**
 * WHICH APP a row's link belongs to, resolved once for all three writers.
 *
 * `undefined` means "the caller did not say", and the answer is the app doing
 * the writing — a bare relative path has always implicitly meant that. `null`
 * means "deliberately no app", which the bulletin fan-out passes on purpose:
 * `/bulletins/<id>` exists in all three apps and one audience can hold a burner
 * and a supplier who need different hosts, so null ("treat as local wherever it
 * is read") is the only value right for both.
 *
 * This exists because the distinction was lost three times over. Each app wrote
 * its own `r.linkApp ?? "<app>"`, and `??` cannot tell "not provided" from
 * "deliberately null": `null ?? "org"` is `"org"`, so every bulletin was stamped
 * for the ORG app, `notificationLinkIsLocal("org", "web")` then returned false
 * on the participant inbox, the link was dropped, and the row rendered inert.
 * A burner received an AfrikaBurn bulletin and could not open it. One helper,
 * one rule, one test.
 */
export function resolveNotificationLinkApp(
  linkApp: NotificationApp | null | undefined,
  writingApp: NotificationApp,
): NotificationApp | null {
  return linkApp === undefined ? writingApp : linkApp;
}

/**
 * Should this app render the row's `link` as a link?
 *
 * Only when the link belongs here. A row minted for another app carries a path
 * this app cannot serve, so linking it produces a 404 — the row still shows,
 * it just does not pretend to be clickable. `null` (pre-migration rows, and
 * anything unstamped) is treated as local, which is the old behaviour exactly.
 */
export function notificationLinkIsLocal(
  linkApp: string | null | undefined,
  thisApp: NotificationApp,
): boolean {
  return !linkApp || linkApp === thisApp;
}
```

*Camp 404 relevance:* `link_app` itself is single-app dead weight, but **the `undefined`-vs-`null` discipline is a general lesson** and the `origin` half of the same migration is directly wanted (§9.3d).

### 11.2 The privacy guard and its non-vacuity test

/**
 * True if any of `needles` appears in the payload's user-visible text
 * (title / body / link). The privacy tests use this to PROVE a built payload
 * leaks no hard-locked value (a phone number, an ID, an emergency contact).
 * Empty/blank needles are ignored so they can't produce false positives.

export function notificationMentionsAny(
  payload: NotificationPayload,
  needles: readonly string[],
): boolean {
  const haystack = [payload.title, payload.body ?? "", payload.link ?? ""]

    const needle = n.trim().toLowerCase();

}

### 11.3 The chunked, provenance-stamping insert

`apps/web/lib/notifications.ts:124-163` (org/suppliers are near-identical)

```ts
/** Rows per INSERT. Eight bound columns each, so Postgres' 65535-parameter
 * ceiling lands at 8191 rows — 1000 keeps a wide margin. */
const NOTIFICATION_INSERT_CHUNK = 1000;

/**
 * Insert notification rows (the event-hook + bulletin-fan-out writer). Accepts
 * an explicit db handle so hooks that already hold one reuse it. No-op on an
 * empty batch. Rows come from the @quagga/core payload builders, which never
 * carry hard-locked private fields.
 */
export async function insertNotifications(
  handle: Database,
  rows: readonly NotificationRow[],
): Promise<void> {
  if (rows.length === 0) return;
  // CHUNKED. Six bound parameters per row against Postgres' 65535-parameter
  // ceiling means a single insert dies at 10923 rows with SQLSTATE 08P01 —
  // and because a bulletin publish wraps this in a transaction, the whole
  // broadcast rolled back. AfrikaBurn is comfortably bigger than 10922 people,
  // so this was a live ceiling on the participant fan-out, not a theoretical one.
  for (let i = 0; i < rows.length; i += NOTIFICATION_INSERT_CHUNK) {
    const chunk = rows.slice(i, i + NOTIFICATION_INSERT_CHUNK);
    await handle.insert(schema.notifications).values(
      chunk.map((r) => ({
        userId: r.userId,
        kind: r.kind,
        title: r.title,
        body: r.body ?? null,
        link: r.link ?? null,
        // Provenance and destination (migration 0021). ONE rule, in
        // @quagga/core: `undefined` means "the caller did not say" and defaults
        // to this app; an EXPLICIT null means "belongs to no single app" and
        // must survive, which is what the bulletin fan-out relies on.
        origin: r.origin ?? null,
        linkApp: resolveNotificationLinkApp(r.linkApp, "web"),
        bulletinId: r.bulletinId ?? null,
      })),
    );
  }
}
```

*Camp 404 relevance:* Camp 404's `dispatchDueBroadcasts` and inline camp-wide publish fan out **unchunked**. At ~80 users that ceiling is never hit, so this is prophylactic — but the pattern is 6 lines and the accompanying test (*"issues ONE insert at exactly 1000 rows and TWO at 1001"*) is the kind of boundary assertion worth having. **Note the two contradicting comments — use the 8-column / 8191 figure, discard the 6 / 10923 one.**

 * Immediate transactional email is sent ONLY for registration decisions and
