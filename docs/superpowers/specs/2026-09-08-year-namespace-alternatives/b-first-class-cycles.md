# Design B — The cycle as a first-class entity

`camp_cycles` + a current-cycle pointer + FKs from everything year-scoped.

---

## 0. What exists today (verified)

**There is no year, edition, cycle or season concept anywhere.** `rg -w
'edition|cycle|season|year' packages/db/src apps/web/lib` returns only prose:
`apps/web/lib/questionnaire.ts:202` ("Your ideas for this year's burn"),
`:313`, `:351`, `:358`, and three unrelated hits about TypeScript *import*
cycles (`packages/db/src/schema.ts:24`, `packages/db/src/relations.ts:10`,
`apps/web/lib/__tests__/camp-config.test.ts:84`). Nothing structural.

But the intent is already written down. `packages/db/src/schema.ts:243-245`:

> Account + history persist across the yearly camp reset; per-burn data in
> other tables is cleared.

and `packages/db/src/schema.ts:375-376` on `burner_profiles`:

> One row per user; persists across the yearly reset.

So the codebase has *always* assumed a yearly reset exists. Nothing implements
one. This design implements it.

### The constraints that shape everything below

Four facts from the existing schema do more to determine the design than any
preference of mine:

| Fact | `file:line` | Consequence |
|---|---|---|
| `required_actions` is UNIQUE on `(user_id, action_key)` — a **unique index**, not a PK | `schema.ts:672-675` | One gate row per user per key, ever. A rollover cannot "add next year's gate" without widening this. Cheap to widen (index, not constraint). |
| `questionnaire_responses` is UNIQUE on `(user_id, definition_key)` — also an index, over a surrogate `id` PK | `schema.ts:1524-1527` | One latest-answer row per user per form. Re-answering **overwrites last year**. This is the single biggest threat to "historical answers must remain readable". |
| `openActivation` upserts gates with `status: "pending", completedAt: null` | `activations.ts:116-130` | **The re-arm primitive already exists.** A rollover does not need new gating machinery — it needs to call this. |
| `closeActivation` expires pending gates rather than deleting them, explicitly "preserving metrics" | `questionnaire-lifecycle.ts:246-254` | The house rule is already mark-don't-delete. The rollover inherits it. |

Two more that matter:

- `classifyChange` (`packages/types/src/questionnaire-builder.ts:461-486`)
  compares **only** the field map and the `visibleIf` map. It never inspects
  top-level keys like `title`. A new top-level `carryOver` flag therefore
  classifies as **cosmetic** with zero code change — no version bump, open
  activations keep serving (`questionnaire-lifecycle.ts:114-116`). That is
  exactly right: toggling carry-over doesn't change the questions, so a member
  mid-form must not be interrupted.
- `computeAudience` (`packages/db/src/audience.ts:35`) already filters out
  `isSystem` and `sanitised` users. Every rollover fan-out inherits that for
  free.

### Repo rules in force

`packages/db/src/schema.ts` is the only hand-authored DDL source;
`packages/db/migrations/**` is generated by `drizzle-kit` and is append-only —
`0000_initial.sql` is frozen, HEAD is `0018_workable_praxagora.sql`
(`migrations/meta/_journal.json`, idx 18). `ADD COLUMN NOT NULL` needs an
explicit `DEFAULT`. This bites hard in §6 and I do not paper over it.

## 2. The cycle entity

### 2.1 `camp_cycles`

```ts
// --- Camp cycles ---------------------------------------------------------
// The year namespace. One row per burn cycle, in a strictly increasing
// `ordinal` sequence; exactly one is `active` at a time (a partial unique
// index enforces it, mirroring questionnaire_activations_one_open_per_key_idx
// and captain_promotion_open_per_target_idx). Advancing the year archives the
// active row and opens the next — nothing is ever deleted, so a rollover is
// always inspectable and (within a window) reversible.
export const cycleStatusEnum = pgEnum("cycle_status", ["active", "archived"]);

export const campCycles = pgTable(
  "camp_cycles",
  {
    id: uuid("id").defaultRandom().primaryKey(),
    // Human label the captain types: "2026", "AfrikaBurn 2027". Free text —
    // this is a camp's own naming, not a date the app computes.
    label: text("label").notNull(),
    // Strictly increasing, 1-based. The sequence, independent of the label.
    ordinal: integer("ordinal").notNull(),
    status: cycleStatusEnum("status").notNull().default("active"),
    openedAt: timestamp("opened_at", { mode: "date" }).notNull().defaultNow(),
    openedByUserId: uuid("opened_by_user_id").references(() => users.id, {
      onDelete: "set null",
    }),
    closedAt: timestamp("closed_at", { mode: "date" }),
    closedByUserId: uuid("closed_by_user_id").references(() => users.id, {
      onDelete: "set null",
    }),
    // Free-text captain note ("moved to Tankwa week 2"), and the machine-
    // readable record of what the rollover actually did — the same payload
    // written to audit_log, kept here so the cycle row is self-explaining.
    notes: text("notes"),
    rolloverSummary: jsonb("rollover_summary").$type<RolloverSummary>(),
  },
  (c) => ({
    // Exactly one active cycle, enforced in the database. Same shape as
    // questionnaire_activations_one_open_per_key_idx (0018).
    oneActive: uniqueIndex("camp_cycles_one_active_idx")
      .on(c.status)
      .where(sql`${c.status} = 'active'`),
    ordinalUniq: uniqueIndex("camp_cycles_ordinal_idx").on(c.ordinal),
  }),
);
```

`RolloverSummary` is a type-only import from `./cycles` — the same trick
`schema.ts:24-26` already uses for `TeamsConfig` to avoid an import cycle.

### 2.2 The pointer

Two candidate designs for "which cycle is current":

1. The partial unique index **is** the pointer — `WHERE status = 'active'`.
2. An explicit `camp_settings.current_cycle_id`.

I use **both, with the index as the invariant and the column as the read
path**, and that is not two sources of truth — the column is a denormalised
cache with the index as the authority, in the same spirit as
`inventory_items.last_checked_at` (`schema.ts:1100-1101`, "denormalised from
the most recent approved `inventory_updates` row for cheap status-page
queries"). The reason is concrete:

```ts
// camp_settings gains one column
    currentCycleId: uuid("current_cycle_id").references(() => campCycles.id, {
      onDelete: "restrict",
    }),
```

`getTeamsConfig()` (`camp-config.ts:93-100`) already does a `SELECT config FROM
camp_settings LIMIT 1` on every request that touches team config. Adding
`current_cycle_id` to **that same select** makes the current cycle free — zero
additional queries in steady state. Reading it from `camp_cycles` instead
would add a query to every request.

`onDelete: "restrict"` because a cycle must never be deletable while it is
pointed at.

### 2.3 `cycle_memberships` — the per-year membership record

This is the payoff of the first-class-entity angle, and it is what makes
"show me last year's roster" a single query.

```ts
// --- Cycle memberships ---------------------------------------------------
// Who was in the camp for a given cycle, and the facts that were true of them
// THAT year: did they pay, what tier, what rank they held, what terms they had
// consented to. The `users` row keeps the CURRENT-cycle values as a cache (so
// every existing roster query keeps working unchanged — see roster.ts:61); this
// table is the archive and the historical truth. Written on the way out of a
// cycle (final values) and on the way in (reset values), by advanceCycle.
export const cycleMemberships = pgTable(
  "cycle_memberships",
  {
    cycleId: uuid("cycle_id")
      .notNull()
      .references(() => campCycles.id, { onDelete: "cascade" }),
    userId: uuid("user_id")
      .notNull()
      .references(() => users.id, { onDelete: "cascade" }),

    // When this member entered this cycle. Equals the cycle's openedAt for a
    // carried-forward member; a later timestamp for a mid-cycle joiner.
    joinedAt: timestamp("joined_at", { mode: "date" }).notNull().defaultNow(),

    // Per-cycle facts, snapshotted. NOT a live mirror of `users` — these are
    // frozen when the cycle closes.
    duesPaid: boolean("dues_paid").notNull().default(false),
    duesPaidAt: timestamp("dues_paid_at", { mode: "date" }),
    membershipTier: membershipTierEnum("membership_tier"),
    // The rank held during this cycle — "who was a captain in 2026".
    rank: rankEnum("rank").notNull().default("member"),
    // POPIA evidence: the terms version in force for this member that year.
    termsVersion: text("terms_version"),
    termsConsentedAt: timestamp("terms_consented_at", { mode: "date" }),
    approvalStatus: approvalStatusEnum("approval_status")
      .notNull()
      .default("approved"),
  },
  (m) => ({
    pk: primaryKey({ columns: [m.cycleId, m.userId] }),
    userIdx: index("cycle_memberships_user_idx").on(m.userId),
  }),
);
```

Last year's roster, in full:

```sql
SELECT u.display_name, m.rank, m.dues_paid, m.membership_tier,
       array_agg(tm.team) AS teams
FROM cycle_memberships m
JOIN users u ON u.id = m.user_id
LEFT JOIN team_memberships tm
       ON tm.user_id = m.user_id AND tm.cycle_id = m.cycle_id
WHERE m.cycle_id = $lastCycle
GROUP BY u.display_name, m.rank, m.dues_paid, m.membership_tier;
```

That query is impossible today at any price. It is the thing this design buys.

## 3. The FK fan-out — and the honest problem with it

### 3.1 The column

Every **Y** and **S** table gets the identical column:

```ts
    cycleId: uuid("cycle_id").references(() => campCycles.id, {
      onDelete: "restrict",
    }),
```

`onDelete: "restrict"` throughout: a cycle with data in it must not be
deletable. Archiving is the only removal.

Applied to: `car_members`, `team_memberships`, `questionnaire_activations`,
`questionnaire_edits`, `required_actions`, `reimbursements`, `team_budgets`,
`tasks`, `adoptees`, `workshops`, `inventory_updates`, `audit_log`,
`broadcasts`, `questionnaire_responses`. Fourteen tables, one identical
column, plus `camp_settings.current_cycle_id`.

### 3.2 The problem: the column cannot be `NOT NULL`

The brief asks what the default is for existing rows. The rigorous answer is
that **there is no default that works**, and I want to be exact about why
rather than hand-wave it.

`ADD COLUMN cycle_id uuid NOT NULL DEFAULT '<uuid>' REFERENCES camp_cycles(id)`
would be fine *if* a `camp_cycles` row with that id existed. It doesn't:
Postgres applies the default to every existing row and then validates the FK,
which fails against an empty parent table. And the parent row cannot be
created by the migration, because:

- `drizzle-kit generate` emits **DDL only** — never `INSERT`.
- AGENTS.md forbids hand-writing a migration, so I cannot add the `INSERT`
  myself.
- A column `DEFAULT` cannot contain a subquery, so I can't source the id from
  `camp_cycles` at all.

Switching the key from `uuid` to an integer `cycle_ordinal NOT NULL DEFAULT 1`
does not escape this: the FK still needs a parent row with `ordinal = 1`.
The only way to get `NOT NULL` in one generated migration is to **drop the FK**
— which discards the entire point of the first-class-entity angle.

So the column ships **nullable**, and NULL is transiently meaningful for
exactly one deploy. NULL passes any FK check, so the migration succeeds on a
populated database with no seed row.

### 3.3 How NULL stops being meaningful: the adopt step

The repo already has the pattern for "a singleton row a migration cannot
insert" — `camp_settings` itself. Both `bootstrapFirstCaptain`
(`bootstrap.ts:64-67`) and `mutateTeamsConfig` (`camp-config.ts:191-194`) open
with:

```ts
await tx.insert(campSettings).values({ id: true })
  .onConflictDoNothing({ target: campSettings.id });
```

— the *application* lazily ensures the singleton exists, inside a
transaction, idempotently. Cycle adoption is the same move:

```ts
// packages/db/src/cycles.ts

/**
 * The camp's active cycle, creating cycle 1 on first call. Idempotent and
 * self-healing: the fast path is a single indexed read of the camp_settings
 * singleton (folded into the same SELECT getTeamsConfig already does), and the
 * slow path runs exactly once in the camp's life — the deploy after migration
 * 0019. Mirrors bootstrap.ts's lazy singleton ensure.
 */
export async function getCurrentCycle(): Promise<CycleRow> {
  const db = createHttpDb();
  const [row] = await db
    .select({ currentCycleId: campSettings.currentCycleId })
    .from(campSettings)
    .limit(1);
  if (row?.currentCycleId) return loadCycle(row.currentCycleId);
  return adoptFoundingCycle();
}

/**
 * One-time: mint cycle 1 and claim every pre-cycle row for it. Serialised on
 * the camp_settings singleton via SELECT … FOR UPDATE, exactly as bootstrap
 * and mutateTeamsConfig do, so concurrent first requests can't double-mint —
 * the partial unique index camp_cycles_one_active_idx is the backstop.
 */
async function adoptFoundingCycle(): Promise<CycleRow> {
  const { db, pool } = createPooledDb();
  try {
    return await db.transaction(async (tx) => {
      await tx.insert(campSettings).values({ id: true })
        .onConflictDoNothing({ target: campSettings.id });
      const [locked] = await tx
        .select({ currentCycleId: campSettings.currentCycleId })
        .from(campSettings)
        .where(eq(campSettings.id, true))
        .for("update");
      if (locked?.currentCycleId) return loadCycleTx(tx, locked.currentCycleId);

      const [cycle] = await tx.insert(campCycles)
        .values({
          label: String(new Date().getUTCFullYear()),
          ordinal: 1,
          status: "active",
        })
        .returning();

      // Claim every orphan row. Idempotent (WHERE cycle_id IS NULL), set-based,
      // and it can only ever match rows written before migration 0019 — every
      // writer from 0019 onward supplies the column.
      for (const t of YEAR_SCOPED_TABLES) {
        await tx.update(t).set({ cycleId: cycle!.id })
          .where(isNull(t.cycleId));
      }
      // Seed cycle 1's membership rows from the live users table.
      await tx.execute(sql`
        INSERT INTO cycle_memberships
          (cycle_id, user_id, joined_at, dues_paid, dues_paid_at,
           membership_tier, rank, terms_version, terms_consented_at,
           approval_status)
        SELECT ${cycle!.id}, u.id, u.created_at, u.dues_paid, u.dues_paid_at,
               u.membership_tier, u.rank, u.terms_version, u.terms_consented_at,
               u.approval_status
        FROM users u WHERE u.is_system = false
        ON CONFLICT DO NOTHING`);

      await tx.update(campSettings)
        .set({ currentCycleId: cycle!.id, updatedAt: new Date() })
        .where(eq(campSettings.id, true));
      return toCycleRow(cycle!);
    });
  } finally {
    await pool.end();
  }
}
```

This is the design's sharpest edge and I will name it plainly: **between
migration 0019 landing and the first `getCurrentCycle()` call, a
cycle-filtered read would return nothing.** The window is one request, the
fix is inside a transaction, and the backfill touches a few thousand rows on a
30-80 person camp — single-digit milliseconds. If the owner prefers explicit
over automatic, the same function can be fronted by a one-time
`/captains/camp-settings` "name your first year" screen and the lazy path
deleted; the transaction body is identical. I'd ship the lazy version and log
once on adoption.

### 3.4 Why I do not ship a follow-up `SET NOT NULL`

A migration 0020 doing `ALTER COLUMN cycle_id SET NOT NULL` on all fourteen
tables is tempting and I recommend against it:

- The PGlite integration harness truncates every public table between test
  files (`packages/db/src/__tests__/_harness.ts`, the `reset()` function), so
  every test file would have to re-run adoption before writing anything.
- A fresh database restored from `migrations/` alone would be un-writable
  until adoption ran — turning a schema into an ordering puzzle.
- It buys nothing operationally. Every writer from 0019 onward supplies the
  column; the invariant is enforced where invariants in this repo already live
  — in the db-layer function, whose signature makes the argument mandatory
  (§7).

Nullable in DDL, non-null in practice, is the boring choice.

### 3.5 The escape hatch, stated honestly

If the FK genuinely isn't worth §3.3's complexity, the alternative is a plain
`integer cycle_ordinal NOT NULL DEFAULT 1` with **no FK** — following the
existing deliberate precedent at `schema.ts:1505-1507`, where
`questionnaire_responses.definition_key` is "plain text (NOT a FK) so
responses survive a definition delete". That version needs no adopt step, no
backfill, and no NULL window: `ADD COLUMN … NOT NULL DEFAULT 1` drops every
existing row into cycle 1 automatically, in one generated migration.

What it gives up: referential integrity (a typo'd ordinal is silently a new
year), `ON DELETE RESTRICT` protection, and the ability to join a cycle's
label/status without a second lookup. For a system that will accumulate maybe
ten cycles in its life, that is a defensible trade — but it makes the cycle a
*number*, not an *entity*, and the queryable history in §2.3 is the reason to
pay for the entity. I recommend the FK.

## 4. Carry-over, end to end

### 4.1 The type

`packages/types/src/questionnaire-builder.ts`, added to the top-level object at
`:123-128`:

```ts
// Whether this questionnaire's answers survive a cycle rollover. "carry" =
// a member who completed it stays done (their answers are copied into the new
// cycle, flagged as carried); "fresh" = they must answer again, with last
// cycle's answers PREFILLED but not counted as complete. Absent ⇒ "fresh":
// a needless re-ask is a two-minute annoyance a member can see, whereas a
// wrongly-carried answer is silent and the camp acts on stale data.
export const CarryOverPolicy = z.enum(["carry", "fresh"]);
export type CarryOverPolicy = z.infer<typeof CarryOverPolicy>;

export const BuilderQuestionnaire = z.object({
  version: z.string().min(1),
  title: z.string(),
  // Optional so every already-stored definition still parses — no JSONB
  // migration, no backfill.
  carryOver: CarryOverPolicy.optional(),
  pages: z.array(BuilderPage).min(1),
});
```

`.optional()` is load-bearing: `questionnaire_definitions.definition` and every
`questionnaire_versions.definition` snapshot are existing JSONB blobs that must
keep parsing untouched.

**`classifyChange` needs no change.** It walks `fieldMap(prev/next)` and
`visibleIfMap(prev/next)` only (`questionnaire-builder.ts:465-485`) and never
looks at top-level keys — so toggling `carryOver` is **cosmetic**: no version
bump, the current snapshot is overwritten in place
(`questionnaire-lifecycle.ts:114-116, 137-143`), and any open activation keeps
serving. Correct by construction — the questions didn't change, so a member
halfway through a form must not be kicked out. I'd add one regression test
asserting `classifyChange(q, {...q, carryOver: "fresh"}) === "cosmetic"`,
because a future contributor could plausibly "fix" `classifyChange` into a deep
object comparison and silently start bumping versions.

### 4.2 The storage — and the code-questionnaire problem

Three questionnaires have no `BuilderQuestionnaire` at all: `burner_profile`,
`dietary_requirements`, `driver_profile` are code questionnaires with bespoke
pages and tables, and are explicitly reserved against the builder
(`questionnaire-definitions.ts:11-16`). The flag has to reach them too, and
the owner wants it *configurable*, not compiled in. So it also lives in the
existing captain-editable JSONB — `camp-config.ts`:

```ts
export interface CampConfig {
  teams: TeamConfigEntry[];
  /**
   * Per-questionnaire carry-over override, keyed by questionnaire key. The ONLY
   * place code questionnaires (burner_profile / dietary_requirements /
   * driver_profile — see RESERVED_DEFINITION_KEYS) can be configured, and a
   * captain-facing override for builder ones. Absent key ⇒ fall through to the
   * definition's own flag, then to "fresh".
   */
  carryOver?: Record<string, CarryOverPolicy>;
}

// Seeded as the column default alongside DEFAULT_TEAMS. burner_profile carries
// because schema.ts:375-376 already declares it lifetime identity; dietary
// carries because allergies aren't annual; driver is fresh because vehicle,
// seats and arrival/departure dates are per-burn by definition.
export const DEFAULT_CARRY_OVER: Record<string, CarryOverPolicy> = {
  burner_profile: "carry",
  dietary_requirements: "carry",
  driver_profile: "fresh",
};
```

`TeamsConfig` is renamed `CampConfig` with `TeamsConfig` kept as a deprecated
alias — `schema.ts:26` imports it type-only and `resolveTeamsConfig`
(`camp-config.ts:76-87`) already tolerates malformed input by falling back
wholesale, so an old-shaped row keeps working.

Note the drift guard: `apps/web/lib/__tests__/camp-config.test.ts:80-100`
extracts the seed JSONB literal from **three** places (`DEFAULT_CAMP_CONFIG`,
the migration SQL, and the inline default in `schema.ts`) and asserts they
agree. Adding `carryOver` to the seed means the new migration's literal must
match — the test enforces it, which is exactly what you want.

### 4.3 The resolver

One pure function, three layers, precedence top-down:

```ts
// packages/db/src/cycles.ts (pure — unit-testable with no DB, like camp-config)

/**
 * The carry-over policy in force for one questionnaire key.
 *   1. camp_settings.config.carryOver[key] — the captain's explicit choice.
 *   2. the definition's own `carryOver` — the form author's declared intent,
 *      which travels with the form when it is cloned.
 *   3. "fresh" — the safe default (loud, recoverable failure over silent one).
 *
 * Layered exactly as team bindings already are: a stored definition resolved
 * against the LIVE camp config at read time (schema.ts:1452-1455), so a
 * captain's change flows in without rewriting the stored definition.
 */
export function resolveCarryOver(
  key: string,
  definition: { carryOver?: CarryOverPolicy } | null,
  config: CampConfig,
): CarryOverPolicy {
  return config.carryOver?.[key] ?? definition?.carryOver ?? "fresh";
}
```

Resolution reads the **head** definition plus live config at rollover time,
not the pinned `questionnaire_versions` snapshot — the captain's last word
before advancing is what applies. The snapshot's copy is informational.

### 4.4 The gating query that reads it

This is where the cycle key earns its keep, because the answer is almost
entirely *subtraction*.

`required_actions` gains `cycle_id` and its unique index widens:

```ts
  (ra) => ({
    // Widened from (user_id, action_key): one gate per user per key PER CYCLE,
    // so next year's gate coexists with last year's record instead of
    // overwriting it. Still a unique INDEX (not a constraint), so drizzle-kit
    // regenerates it with a cheap DROP INDEX / CREATE INDEX.
    userActionIdx: uniqueIndex("required_actions_cycle_user_action_idx").on(
      ra.cycleId, ra.userId, ra.actionKey,
    ),
    userStatusIdx: index("required_actions_cycle_user_status_idx").on(
      ra.cycleId, ra.userId, ra.status,
    ),
  }),
```

And the gate reader (`activations.ts:209-233`) gains exactly one predicate:

```ts
export async function getPendingRequiredActions(
  userId: string,
  cycleId: string,          // required, not defaulted — see §7
): Promise<PendingRequiredAction[]> {
  // …
    .where(
      and(
        eq(schema.requiredActions.cycleId, cycleId),   // ← the whole feature
        eq(schema.requiredActions.userId, userId),
        eq(schema.requiredActions.status, "pending"),
        eq(schema.requiredActions.blocking, true),
      ),
    )
    .orderBy(asc(schema.requiredActions.createdAt));
}
```

That single line is the year namespace, as seen by `apps/web/app/page.tsx:55`.
Last cycle's rows become invisible to the gate without being touched. Then:

- **`fresh`** → the rollover opens a new activation in the new cycle and calls
  the *existing* `openActivation` (`activations.ts:40-137`), which fans out
  gates through the *existing* `computeAudience`. New cycle, new pending rows,
  member is gated.
- **`carry`** → the rollover opens nothing. No rows in the new cycle ⇒ nothing
  pending ⇒ no gate. **Absence is the mechanism.**

The only other change to `openActivation` is its conflict target
(`activations.ts:116-120`), from two columns to three:

```ts
        .onConflictDoUpdate({
          target: [
            schema.requiredActions.cycleId,
            schema.requiredActions.userId,
            schema.requiredActions.actionKey,
          ],
          set: { /* unchanged */ },
        })
```

Four `onConflictDoUpdate` / `onConflictDoNothing` targets move in total:
`activations.ts:116-120`, `:163-165`, `:325-329`, and
`questionnaire-responses.ts:43-47`.

### 4.5 Responses, history, and the asymmetry I chose

`questionnaire_responses` gains two columns and a widened index:

```ts
    cycleId: uuid("cycle_id").references(() => campCycles.id, {
      onDelete: "restrict",
    }),
    // Set when this row was COPIED FORWARD by a rollover rather than answered
    // in this cycle. Makes carry-over inspectable: you can always tell an
    // answer that was carried from one that was freshly given, and trace it to
    // the cycle it came from. NULL = answered in this cycle.
    carriedFromCycleId: uuid("carried_from_cycle_id").references(
      () => campCycles.id, { onDelete: "set null" },
    ),
  // …
    userDefIdx: uniqueIndex("questionnaire_responses_cycle_user_def_idx").on(
      r.cycleId, r.userId, r.definitionKey,
    ),
```

Widening this index is what stops re-answering from destroying last year.
Today `completeBuilderResponse` (`activations.ts:325-337`) upserts on
`(user_id, definition_key)` and **overwrites** — after this change, answering
in cycle 2 inserts a new row and cycle 1's is untouched.

**Carried answers are copied, not resolved by fallback.** For a `carry` key
the rollover inserts a fresh row in the new cycle with the same `responses`,
same `definition_version`, `completedAt` preserved, and
`carried_from_cycle_id` set. The alternative — leaving no row and having reads
fall back to the newest prior cycle — makes every read of every response a
correlated lookup, forever, to save 80 rows per form per year. Copying keeps
every read a single equality filter, which is the reason to pay for the key at
all. Nothing is destroyed: last cycle's row stays exactly where it was.

**The asymmetry, owned.** I do **not** cycle-key `burner_profiles`,
`dietary_requirements` or `driver_profiles`. They stay one row per user. Why:

- `burner_profiles` is *documented* as lifetime (`schema.ts:375-376`), and all
  three are PK'd on `user_id` (`:382, :402, :423`) — keying them means a PK
  change on tables with 24 / 6 / 19 references across five source files each.
- Their history already exists. `questionnaire_edits` (`schema.ts:603-641`) is
  an append-only per-field before→after log with `version` and `createdAt`,
  indexed on `(user_id, questionnaire_key, created_at)` (`:628-632`). Stamping
  it with `cycle_id` makes "what did they answer last year" a clean query
  against a table *designed* for the question.
- A `fresh` code questionnaire still re-gates perfectly: new activation → new
  `required_actions` row in the new cycle → member gated → they re-answer →
  the domain table is overwritten **and** `questionnaire_edits` records the
  diff. Gate re-armed, history preserved, zero PK churn.

The camp's real "last year" questions — who was here, who paid, which team,
what did they say on the forms — are answered by `cycle_memberships`,
`team_memberships` and `questionnaire_responses`. Last year's vehicle
registration is not one of them.

### 4.6 The rule that closes the silent hole

Carry-over means **"don't re-ask someone who already answered"** — not "let
everyone through". So:

> For a `carry` key, a member with **no completed prior response** is gated in
> the new cycle anyway.

Without this rule, a member who ignored last year's carry-over questionnaire
would sail into the new year with no answer on file and no gate — silently.
The rule needs no new mechanism: the rollover computes the set of members with
a completed prior response, copies those forward, and opens an
`scope: 'individual'` activation (a scope that already exists,
`schema.ts:135`) targeting the remainder.

## 6. The rollover action

`packages/db/src/cycles.ts`, exported through `package.json` as
`"./cycles": "./src/cycles.ts"` alongside the other 25 entries.

### 6.1 Preview first — it says what it will do

The brief requires the action to announce itself. `previewRollover()` is a
read-only function that runs the same computation and returns exactly what the
confirm screen renders:

```ts
export interface RolloverPreview {
  from: { id: string; label: string; ordinal: number };
  proposedLabel: string;
  questionnaires: Array<{
    key: string; title: string;
    policy: CarryOverPolicy;
    /** completed prior responses that will be copied forward */
    carriedMembers: number;
    /** members who will be gated again */
    regatedMembers: number;
    /** carry-over key, but never answered — gated anyway (§4.6) */
    unansweredMembers: number;
  }>;
  activationsToClose: number;
  pendingActionsToExpire: number;
  membersCarriedForward: number;
  teamMembershipsCopied: number;
  duesReset: number;
  untouched: string[];   // "approval status", "terms consent", …
}
```

`untouched` is deliberate: the screen states what will *not* change as
prominently as what will, because that is where a captain's fear lives.

### 6.2 Confirm

Captain-only, gated with the same shape as
`apps/web/app/captains/camp-settings/actions.ts:44-63` (signed in → camp
access → approved → `requireClearance(deriveViewerRank(...), "captain")`).
Plus: the captain must **type the outgoing cycle's label** to confirm —
`advanceCycle({ label, confirmLabel, actorUserId })` rejects unless
`confirmLabel === current.label`. The "type the name to proceed" pattern,
which costs nothing and makes the preview mandatory reading.

Lives at `/captains/camp-settings` under the team editor
(`camp-settings/page.tsx:53-54`), which is already the camp-wide config
surface.

### 6.3 The transaction, step by step

One pooled transaction (`createPooledDb` — the HTTP driver has no
transactions, per `camp-config.ts:180-182`):

1. **Lock.** `insert(campSettings).values({id:true}).onConflictDoNothing()`
   then `SELECT … FOR UPDATE` on the singleton. Identical to
   `bootstrap.ts:64-72` and `camp-config.ts:190-199`. Two captains tapping at
   once: one wins, the other sees the new cycle and gets `already-advanced`.
2. **Read the active cycle.** None ⇒ this is adoption (§3.3), not a rollover;
   run that and return.
3. **Freeze the outgoing cycle's membership facts.** `UPDATE cycle_memberships
   SET dues_paid = u.dues_paid, dues_paid_at = …, membership_tier = …,
   rank = u.rank, terms_version = …, terms_consented_at = …,
   approval_status = u.approval_status FROM users u WHERE …` for the outgoing
   cycle. The archive write happens **before** any reset, so nothing is lost.
4. **Archive the outgoing cycle.** `status = 'archived'`, `closedAt`,
   `closedByUserId`.
5. **Close every open activation** for the outgoing cycle: activation
   `status='closed'`, its still-pending `required_actions` → `'expired'`.
   Byte-for-byte the loop already in `unpublishDefinition`
   (`questionnaire-lifecycle.ts:199-213`).
6. **Open the new cycle.** Insert `camp_cycles` with `ordinal + 1`,
   `status='active'`. Step 4 already archived the outgoing row, so
   `camp_cycles_one_active_idx` cannot collide.
7. **Repoint** `camp_settings.current_cycle_id`.
8. **Admit the members.** Insert one `cycle_memberships` row per non-system,
   non-sanitised, non-rejected member with the *reset* values (`dues_paid =
   false`, `membership_tier = null`, `rank` and `approval_status` and terms
   carried from `users`).
9. **Carry the roster.** Copy `team_memberships` (with `is_lead`) into the new
   cycle, unless `resetTeamMemberships`.
10. **Reset the `users` cache.** `dues_paid = false`, `dues_paid_at = null`,
    `membership_tier = null`. Nothing else on `users` is touched (§5).
11. **Copy carried responses.** For every key resolving `carry`, one
    `INSERT … SELECT` per key into `questionnaire_responses` with
    `cycle_id = new`, `carried_from_cycle_id = outgoing`, `activation_id =
    null`, `completedAt` preserved.
12. **Re-arm the fresh ones.** For each key resolving `fresh` that had an
    activation in the outgoing cycle, insert a matching activation in the new
    cycle (same `scope` / `team` / `blocking`, `dueAt` cleared) and fan out via
    the existing `openActivation`. Plus the §4.6 individual-scope activation
    for `carry` keys' unanswered members.
13. **Record.** `audit_log` row `action = 'cycle.advanced'` with the full
    `RolloverSummary` in `metadata`, and the same payload onto
    `camp_cycles.rollover_summary` so the cycle row explains itself.
14. **Announce** (optional, default off). One `broadcasts` row, `kind:
    'system'`, `presentation: 'popup'` (`schema.ts:198-201`) — "Camp 404 has
    moved to 2027" — so re-gating isn't mysterious. Reuses the notification
    engine wholesale.

Steps 11 and 12 use `openActivation` and the existing upsert semantics rather
than new SQL. There is no parallel gating machinery in this design.

### 6.4 Reversibility

Nothing was deleted, so undo is mechanical: `undoLastRollover()` re-activates
the outgoing cycle, archives the new one, repoints `camp_settings`, restores
`users.dues_paid` / `membership_tier` from the outgoing `cycle_memberships`
snapshot (step 3 is what makes this possible), and re-opens the activations
step 5 closed.

I'd gate it: **allowed only while the new cycle has no member writes** — no
`questionnaire_responses` with `carried_from_cycle_id IS NULL`, no
`required_actions` with `status = 'completed'`, in the new cycle. Past that
window undo becomes a judgement call about whose fresh answers to discard, and
the honest remedy is that a captain re-declares the old label as a new cycle.
Either way **no data is ever lost** — that is the guarantee the design
actually makes, and it's stronger than reversibility.

## 7. Migration plan under append-only rules

HEAD is `0018_workable_praxagora.sql`. Everything below is produced by editing
`packages/db/src/schema.ts` and running `pnpm --filter @camp404/db db:generate`.
No migration is hand-written.

### Migration 0019 — the year namespace (one `db:generate`)

Additive, in one file:

- `CREATE TYPE cycle_status AS ENUM('active','archived')` — a **new** type, so
  `CREATE TYPE`, never the last-resort `ALTER TYPE … ADD VALUE`.
- `CREATE TABLE camp_cycles` (+ `camp_cycles_one_active_idx`,
  `camp_cycles_ordinal_idx`).
- `CREATE TABLE cycle_memberships`.
- `ALTER TABLE camp_settings ADD COLUMN current_cycle_id uuid` + FK. Safe: the
  table holds ≤1 row and the value is NULL.
- `ALTER TABLE camp_settings ALTER COLUMN config SET DEFAULT '…'::jsonb` — the
  seed grows a `carryOver` object. The three-way drift test
  (`camp-config.test.ts:80-100`) enforces that the literal, the migration SQL
  and `DEFAULT_CAMP_CONFIG` agree.
- `ADD COLUMN cycle_id uuid` **nullable** + FK `ON DELETE RESTRICT`, on all
  fourteen: `car_members`, `team_memberships`, `questionnaire_activations`,
  `questionnaire_edits`, `required_actions`, `reimbursements`, `team_budgets`,
  `tasks`, `adoptees`, `workshops`, `inventory_updates`, `audit_log`,
  `broadcasts`, `questionnaire_responses`.
- `ADD COLUMN carried_from_cycle_id uuid` + FK on `questionnaire_responses`.
- `DROP INDEX` / `CREATE UNIQUE INDEX` for the two widened unique **indexes**
  (`required_actions_user_action_idx`, `questionnaire_responses_user_def_idx`)
  and the widened `questionnaire_activations_one_open_per_key_idx`. These are
  indexes, not constraints — cheap and low-risk.

**Default for existing rows: NULL**, on every one of the fourteen. §3.2 shows
why no other value is reachable from a generated migration; §3.3 is how NULL
stops existing.

### Migration 0020 — the two real PK changes (a second `db:generate`)

`team_memberships` (PK `(user_id, team)`, `schema.ts:487`) and `team_budgets`
(PK `team`, `schema.ts:797`) cannot hold two rows for the same key across
cycles, so carry-forward would violate them. This is the one place the design
spends non-additive DDL. Both get a surrogate PK plus a widened unique index:

```ts
export const teamMemberships = pgTable(
  "team_memberships",
  {
    id: uuid("id").defaultRandom().primaryKey(),   // ← new surrogate
    cycleId: uuid("cycle_id").references(() => campCycles.id, {
      onDelete: "restrict",
    }),
    userId: uuid("user_id").notNull().references(() => users.id, {
      onDelete: "cascade",
    }),
    team: teamEnum("team").notNull(),
    isLead: boolean("is_lead").notNull().default(false),
    createdAt: timestamp("created_at", { mode: "date" }).notNull().defaultNow(),
  },
  (tm) => ({
    cycleUserTeam: uniqueIndex("team_memberships_cycle_user_team_idx").on(
      tm.cycleId, tm.userId, tm.team,
    ),
    teamIdx: index("team_memberships_cycle_team_idx").on(tm.cycleId, tm.team),
  }),
);
```

Kept as a **separate** `db:generate` from 0019 deliberately. If drizzle-kit
emits the `DROP CONSTRAINT` / `ADD COLUMN` / `ADD PRIMARY KEY` in an order
Postgres rejects, AGENTS.md forbids fixing the SQL by hand — the sanctioned
fix is to split the schema.ts change across more `db:generate` runs until the
generated order is valid. Isolating the risky change makes that cheap. These
are a ~30-row and an 8-row table; the migration itself is trivial.

`team_budgets` gets the same treatment: surrogate `id`, unique `(cycle_id,
team)`. The alternative — leaving budgets un-scoped, one row per team forever
— is rejected: per-year budget is the most obviously year-shaped thing in the
camp.

### No migration 0021

No `SET NOT NULL` pass, for the reasons in §3.4.

### Verification

`packages/db/src/__tests__/_harness.ts` replays the committed migrations into

**The mitigation that makes it tractable:** thread `cycleId` as a **required**
parameter through the db-layer signatures — `getPendingRequiredActions(userId,

defaulting it to "current" inside each function. `tsc --noEmit` (already a
turbo task, `packages/db/package.json` scripts) then enumerates every call site
for you: "Expected 2 arguments, but got 1", one per site, until the list is
empty. A default would silently miss the historical-read call sites, which is
precisely where a bug would hide.

This is a one-time mechanical cost — a couple of days — not an ongoing tax.
After it, adding a year-scoped feature is one more column.

### The other costs

- **The NULL window** (§3.3) — one request wide, self-healing, but real.
- **Two PK changes** (§7) — the only non-additive DDL, on a 30-row and an
  8-row table.
- **~80 extra rows per carried form per year** in `questionnaire_responses`
  (§4.5). A camp of 80 people with five forms and ten cycles accumulates 4,000
  rows. Nothing.
- **`cycle_memberships` doubles the "who is a member" question** into a live
  cache (`users`) and an archive (`cycle_memberships`). Mitigated by keeping
  `users.dues_paid` authoritative-for-now, so every existing roster query
  (`roster.ts:60-61, 102-105`) is untouched.

### What it buys

Per-cycle stats without a single new aggregate table. "Show me the 2026
roster" as one join. An unambiguous answer to "which year did this response
belong to" that is a column, not an inference from timestamps. A rollover that
is a transaction rather than an ops runbook. And a schema where next year's
features are born year-aware because the column is already there.

## 9. What the member sees

`apps/web/app/page.tsx:55` is the whole story: `nextGate(await
getPendingRequiredActions(campUser.id))`, with the cycle predicate added.

- **Carry-only member.** Nothing changes. No gate, straight to home. Their
  answers are still visible under `/tools/forms/…` because step 11 copied a
  row into the new cycle. If step 14's announcement is on, a dismissable popup
  says the camp has moved to 2027.
- **Member with a `fresh` questionnaire.** Redirected exactly as the first
  time — `/onboarding/questionnaire` for `burner_profile` via the static route
  map (`required-actions.ts:9-13`), or `/questionnaires/<newActivationId>` for
  a builder form via the activation branch (`:35-37`). No new routing.
- **Prefill, and the trap in it.** The runner seeds last cycle's answers so
  re-answering is mostly tapping Continue. That read **must not** carry
  `completedAt`, or the gate self-satisfies and "fresh" silently becomes
  "carry":

```ts
/**
 * The member's answers for the runner: this cycle's row if one exists,
 * otherwise the most recent prior cycle's as a SEED. A seeded read always
 * reports completedAt = null regardless of the prior row's value — a prefill
 * is a convenience, never a completion, or a "fresh" questionnaire would
 * satisfy its own gate.
 */
export async function loadResponseForRunner(
  userId: string, definitionKey: string, cycleId: string,
): Promise<{ responses: QuestionnaireResponses;
             completedAt: Date | null;
             seededFromCycleId: string | null }>;
```

The UI shows a quiet line — *"Prefilled from 2026. Check it's still right."* —
which is the honest framing of what a rollover is asking for.

- **The gate is real.** `completedAt` stays null until submit;
  `completeBuilderResponse` (`activations.ts:304-366`) writes the response and
  satisfies the gate in one transaction, so a completed response can never
  coexist with a pending gate. Unchanged behaviour, new cycle.

### Edge cases named in the brief

**Joined mid-cycle.** Nothing special. They have a `cycle_memberships` row with
`joinedAt` inside the cycle, and roll forward like anyone else.

**Joins *after* the rollover.** `ensureCampUser` → `seedBurnerProfileAction`
(`apps/web/lib/users.ts:196-205`) seeds their gate; it now stamps the
**current** cycle. `schema.ts:534-536` describes reconciling new joiners
against still-open activations — that reconciliation now only sees the current
cycle's activations, so a fresh joiner gets exactly today's gates and none from
a closed year. That falls out of the cycle filter for free.

**Never answered last year's questionnaire.** Their pending row is `expired` by
step 5 (terminal, non-gating, preserved). If the key is `fresh` they get a new
`pending` row in the new cycle — gated like everyone. If the key is `carry`,
§4.6 gates them too, because there was nothing to carry. The preview counts
them under `unansweredMembers`, so the captain sees the number before
advancing.

**Sanitised ("Lost Cat #N") accounts.** Excluded from admission and fan-out via
`computeAudience`'s existing filter (`audience.ts:35`).

**A member rejected last cycle.** `approval_status` is untouched (§5), so they
stay rejected and stay out. Their `cycle_memberships` row records that they
were rejected in that cycle.

## 10. What I deliberately did not do

1. **No background job, no cron, no ops runbook.** Rollover is one synchronous
   transaction over ≤80 members. A camp this size should never wait on a
   worker for a once-a-year action.
2. **No yearly data migration and no table-per-year.** The DDL is written once,
   in 0019/0020. Every subsequent rollover is `INSERT` + `UPDATE`.
3. **Did not cycle-key `burner_profiles` / `dietary_requirements` /
   `driver_profiles`.** PK churn across five files each, for history that
   `questionnaire_edits` already keeps. §4.5 owns the asymmetry.
4. **Did not cycle-key `inventory_items`, `documents`, `recipes`,
   `invite_codes`.** Lifetime assets — the camp owns the gazebo in 2027 too.
5. **Deleted nothing.** Every rollover step is an insert, an archive flag, or a
   reset preceded by a snapshot. `carried_from_cycle_id` and
   `rollover_summary` make the result inspectable after the fact.
6. **Did not reset `approval_status` or `terms_consented_at`.** §5 — the two
   fields where "reset it, it's a new year" is actively dangerous.
7. **No `ALTER TYPE … ADD VALUE`.** The one new enum is a new type.
8. **Did not teach `classifyChange` about `carryOver`.** It already reads as
   cosmetic, which is the correct answer. §4.1 adds a regression test instead
   of a code change.
9. **No multi-camp / multi-tenant.** Cycles are a linear sequence for one camp.
   No `camp_id`, ever.
10. **No client data layer, no offline, no sync.** The DB stays the truth.
11. **Did not ship a `SET NOT NULL` follow-up.** §3.4.
12. **Did not build a per-cycle recipe menu or a per-cycle inventory audit.**
    Both are real and both are the *next* feature, not this one.
